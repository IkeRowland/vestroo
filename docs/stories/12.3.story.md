## Story

- As **fulfilment staff**, I need **`/ops/bookings`** with **multi-select filter chips** for **status**, **payment status**, **intent**, and **client type**, so that **I do not miss bookings** that are invisible on **`/ops/trips`**, **`/ops/board`**, or fulfil sub-tabs (**US-B1**).

## Acceptance Criteria (ACs)

### US-B1 — Unified ops bookings queue (Theme B)

1. **Data source:** The list is driven from **`bookings`** (Supabase query from the **`bookings`** table). **Joins** (e.g. vehicle / trip preview) are **optional** and used **only** for display. The **default** list query is **not** “trips-only” or an **inner join to trips** as the rule for which bookings appear — **bookings without trips** remain in the result set unless **explicitly** filtered out by chips (none applied by default) — epic **US-B1** line **112**.

2. **Default view — no pre-set filters:** On initial navigation to **`/ops/bookings`** with **no** chip-driven narrowing, **every** booking row matching RLS is **visible**, regardless of **`status`**, **`booking_intent`**, or **`payment_status`**. This includes **`booking_intent='trip_request'`** and rows **without** linked trips — epic **US-B1** line **113**; aligns **Q7**.

3. **Chips — multi-select on four dimensions:**

   - **Status:** Multi-select; allowed values are those enforced by **`bookings_status_check`** (see types / migration — **do not invent SQL** in this story).
   - **Payment:** Multi-select; allowed values are those enforced by **`bookings_payment_status_check`**.
   - **Intent:** Multi-select; allowed values are those enforced by **`bookings_booking_intent_check`** (or the project’s existing **booking intent** enum / generated union — same source as DB).
   - **Client type:** Multi-select **`walk_in`**, **`account_client`**, and/or **both** selected (semantics: filter matches **any** of the selected types — **OR** within this dimension; **AND** across dimensions when multiple chip groups active — epic line **114** “both” = staff can include either or both types via multi-select).

4. **Predicates & empty states:** Filter logic is **documented** in code comments and **PR description** (how multi-select combines: **OR** within a dimension, **AND** across dimensions unless product explicitly chooses otherwise — document the chosen rule). When the filtered result is empty, the **empty state** explains **why** (e.g. no rows match the current chip combination), per Epic **E2** empty-state pattern — epic **US-B1** line **115**.

5. **Row minimum columns:** Each row shows at minimum: **`payment_reference`**, **`customer_name`**, **`customer_email`**, **`pickup_datetime`**, **`status`** badge, **`payment_status`** badge, **`client_type`** badge, **`booking_intent`** badge, **`total_amount`**, and either a **vehicle preview** (when assignable data exists) **or** a clear **“not yet assigned”** (or equivalent) marker — epic **US-B1** line **116**.

6. **Row navigation:** Clicking a row navigates to a **booking detail** view **if** one exists in the app; **otherwise** navigates to a **documented placeholder** route (or same route with placeholder UI) for **Epic 13/14** to wire — epic **US-B1** line **117**.

### Cross-cutting — URL state & bookmarkability

7. **Bookmarkable filters:** Chip selections are reflected in the **URL** so staff can bookmark or share a filtered view. **All four dimensions** including **`payment_status`** must participate in URL serialization. **Default** landing: **no** filter params → **no** `.eq` (or equivalent) filters on those axes — unfiltered list. When chips are active, serialization must support **multi-select** per dimension (**OR** semantics within dimension per **AC4**). **Implementation note:** Existing code may use **`src/lib/ops-bookings-queue-query.ts`** with a **single-value** contract for some params — **extend or replace** (e.g. repeated query keys, comma-separated lists, or dedicated `payment=` / `status=` params) so the **bookmarkable** URL matches chip state; **document the chosen contract in the PR**.

### Cross-cutting — Accessibility (**E2**-adjacent)

8. **a11y:** Chip controls are **keyboard-operable** and expose **accessible names** / state (selected filters, clear filters). The list is exposed as a sensible landmark structure consistent with other ops list pages (**fulfil** prior art).

### Cross-cutting — Loading & errors (**E2**)

9. **Loading / error:** While the list query loads, show a **loading** state consistent with ops **E2**. On **failure**, show a clear **error** with **retry** — **no** silent empty list implying zero bookings.

### Cross-cutting — Ops navigation

10. **Ops nav:** **`/ops/bookings`** is reachable from **`src/features/ops/ops-nav-config.ts`** (or equivalent) in line with **12.2** — no regression; label matches product (“Bookings” or agreed string).
