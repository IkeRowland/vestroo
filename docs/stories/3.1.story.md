# Story 3.1: Data Persistence

## Status: Review

## Story

- As a **system administrator**
- I want **all user, booking, route, and pricing data to be securely stored in the Supabase (PostgreSQL) database**
- so that **data integrity is maintained, the system can scale reliably, and all application data is persisted across deployments and server restarts**

## Acceptance Criteria (ACs)

1. **AC1:** All PayloadCMS collections (Routes, VehicleTypes, PricingRules, Bookings, Media, Users) MUST persist data to Supabase PostgreSQL database via the postgres adapter.

2. **AC2:** All PayloadCMS globals (Homepage, AboutUs, Contact, SiteSettings) MUST persist data to Supabase PostgreSQL database via the postgres adapter.

3. **AC3:** The database connection MUST be properly configured with connection pooling, timeout settings, and error handling.

4. **AC4:** Database migrations MUST be automatically handled by PayloadCMS when collections or globals are first accessed or schema changes are detected.

5. **AC5:** All database operations MUST use the configured `DATABASE_URL` environment variable (or `DATABASE_URI` as fallback) for connection.

6. **AC6:** The database connection MUST validate connection string format and provide clear error messages if configuration is invalid.

7. **AC7:** Database connection errors MUST be handled gracefully with appropriate logging and user-friendly error messages.

8. **AC8:** The system MUST support both development and production database configurations without code changes.

## Dev Technical Guidance

### Database Configuration

The database persistence is handled by PayloadCMS 3.0 using the `@payloadcms/db-postgres` adapter. The configuration is in `payload.config.ts`:

**Key Configuration Points:**
- **Adapter:** `postgresAdapter` from `@payloadcms/db-postgres`
- **Connection String:** Uses `DATABASE_URL` environment variable (with `DATABASE_URI` as fallback)
- **Connection Pooling:** Configured with:
  - `connectionTimeoutMillis: 10000` (10 seconds)
  - `idleTimeoutMillis: 30000` (30 seconds)
  - `max: 10` (maximum pool size)
- **Migrations:** PayloadCMS automatically handles migrations when schema changes are detected

**Reference:** See `payload.config.ts` for current configuration. Environment variable validation is implemented in the `getEnv()` function.

### Environment Variables

Required environment variables (see `docs/environment-vars.md`):

- **`DATABASE_URL`** (required): PostgreSQL connection string from Supabase project settings
  - Format: `postgresql://[user]:[password]@[host]:[port]/[database]`
  - Can use `DATABASE_URI` as fallback (for compatibility)
- **`SUPABASE_SERVICE_ROLE_KEY`** (server-side only): For server-side database operations that bypass RLS

**Reference:** `docs/environment-vars.md#Server-Side-Variables` for complete environment variable documentation.

### Migration System

PayloadCMS 3.0 with postgres adapter automatically handles migrations:
- Tables are created automatically when collections/globals are first accessed
- Schema changes trigger automatic migrations
- Migration settings can be configured in `payload.config.ts` (see PayloadCMS documentation)

**Note:** No manual migration files are required. PayloadCMS handles all DDL operations automatically.

### Error Handling Patterns

When implementing error handling:

1. **Connection Errors:** Catch and log connection failures, provide user-friendly message
2. **Query Errors:** Catch database query errors, log details server-side, return generic error to client
3. **Validation Errors:** Use Zod schemas for input validation before database operations
4. **Logging:** Use appropriate log levels (error, warn, info) - never log sensitive data

**Reference:** `docs/operational-guidelines.md#Security-Best-Practices` for security considerations.

### Testing Database Persistence

To verify data persistence:

1. **Via PayloadCMS Admin:** Create/update records in admin panel, verify in Supabase dashboard
2. **Via PayloadCMS Local API:** Use `payload.find()` or `payload.create()` in server actions, verify in Supabase
3. **Direct Supabase Query:** Use Supabase dashboard SQL editor to query tables directly
4. **Restart Test:** Create data, restart Next.js server, verify data still exists

**Supabase Dashboard Access:**
- Navigate to your Supabase project → Database → Tables
- Tables are named based on PayloadCMS collection/global names (typically pluralized, e.g., `routes`, `bookings`)

### Project Structure Alignment

Database-related files should be organized as follows:

- **Collections:** `src/collections/*.ts` - PayloadCMS collection definitions
- **Globals:** `src/globals/*.ts` - PayloadCMS global definitions
- **Config:** `payload.config.ts` - Main PayloadCMS configuration with database adapter
- **Types:** `src/types/payload-types.ts` - Auto-generated TypeScript types (created by PayloadCMS)

**Reference:** `docs/project-structure.md` for complete project structure.

### Architecture Context

Data flow for persistence:
1. **Admin Panel:** PayloadCMS Admin UI → PayloadCMS Local API → Supabase PostgreSQL
2. **Server Actions:** Next.js Server Actions → PayloadCMS Local API → Supabase PostgreSQL
3. **ISR/SSR:** Next.js Server Components → PayloadCMS Local API → Supabase PostgreSQL (with caching)

**Reference:** `docs/architecture.md#High-Level-Overview` for complete architecture overview.

### Security Considerations

- **Connection String:** Never expose `DATABASE_URL` to client-side code
- **Service Role Key:** `SUPABASE_SERVICE_ROLE_KEY` is server-side only, bypasses RLS
- **Row Level Security:** Supabase RLS policies should be configured for direct Supabase client access (if used)
- **PayloadCMS Access Control:** Collections use PayloadCMS Access Control functions (not RLS) for authorization

**Reference:** `docs/operational-guidelines.md#Security-Best-Practices` for security guidelines.
