**Constraining principles (from epic Theme B):**

- **Trustworthy errors:** Ops staff see **actionable** failure UI for **server actions** and **realtime subscriptions**; **no** raw stack traces, tokens, or secrets in the browser.
- **Freshness contract:** Each ops surface has a **documented** strategy: **realtime** (subscribe), **explicit refresh**, or **revalidate** — **consistent** per page; long-lived sessions do not **silently** show stale booking/trip data **without** user-visible indication.
- **Observable ops actions:** Server actions used in ops flows emit **structured** logs with **correlation**, **level**, **outcome**, and **PII minimization**.

## Story

- As **ops staff** working in the console
- I need **clear, consistent error UI** when **server actions** or **subscriptions** fail, with a **recovery path** (retry, refresh, or navigate)
- so that I can **recover quickly** without guessing what broke, and **never** see leaked technical secrets (**US-B1**)

- As **ops staff** monitoring **bookings** and **trips** over **long sessions**
- I need **fresh data** when data changes, following a **documented** approach on each page (**realtime** where subscribed, **or** explicit refresh, **or** revalidate)
- so that I am **not misled by silent stale state** — if data may be stale, I get **visible feedback** (**US-B2**)

- As an **engineer** supporting ops flows
- I need **structured logs** from **server actions** (correlation ids / action names / safe entity ids, level, outcome) with **minimal PII**
- so that I can **debug production issues** safely and correlate client-visible errors with server-side events (**US-B3**)

## Acceptance Criteria (ACs)

### US-B1 — Clear error UI and safe copy (Theme B)

1. **Shared error surface:** A shared **`OpsErrorState`** (in **`src/features/ops/components/OpsErrorState.tsx`** or an agreed equivalent under **`src/features/ops/components/`**) **MUST** be used on **core ops routes** under **`src/app/(ops)/ops/`** wherever user-visible **server action** or **subscription** failures are surfaced — **[`docs/epic-11.md`](../epic-11.md)** Theme B (**US-B1**).

2. **Recovery paths:** For those failures, the UI **MUST** offer at least one **documented** recovery affordance — **retry** (where idempotent / safe), **refresh** (reload data or router refresh), or **navigate** (link back to a safe hub) — **US-B1** AC.

3. **No leaks:** User-facing messages and toast/console exposure **MUST NOT** include raw **stack traces**, **JWTs**, **service-role keys**, **full SQL errors**, or other **secrets** — **US-B1** AC.

### US-B2 — Data freshness contract (Theme B)

4. **Per-page documentation:** A **normative** description (small **`docs/`** file such as **`docs/ops-data-freshness.md`**, or a section agreed with the team in an existing ops doc) **MUST** list **each** primary **`src/app/(ops)/ops/**` page (or grouped layout) and its strategy: **realtime** (and which channel/topic), **explicit refresh** (control + behaviour), or **revalidate** (pattern and trigger) — **US-B2** AC.

5. **Consistency:** Pages that **subscribe** via **`src/features/ops/components/OpsBoardRealtimeBridge.tsx`** (or successor) **MUST** follow one **consistent** pattern for **subscription errors** and **reconnect** / **fallback** messaging aligned with **AC1–AC3** — **US-B2** AC.

6. **No silent staleness:** On **long-lived** sessions, if a page **does not** receive updates for booking/trip-affecting data and **may** be stale, the UI **MUST** provide **user-visible** indication (banner, stale badge, last-updated timestamp, or equivalent) **or** an explicit refresh path — **US-B2** AC.

### US-B3 — Structured server-action logging (Theme B)

7. **Structured fields:** Ops-related **server actions** in **`src/actions/ops*.ts`** (e.g. **`opsDispatch.ts`**, **`opsFulfil.ts`**, **`opsCompliance.ts`**, **`opsInvoicingHooks.ts`**, and any **`ops*.ts`** added for ops) **MUST** emit **structured** log lines or JSON logs including: **action name** (or stable identifier), **outcome** (`success` / `failure` / `validation_error` / etc.), **level** (e.g. `info` / `warn` / `error`), and **correlation** (request id and/or **safe** entity ids such as booking/trip UUIDs **where** already used in app code) — **US-B3** AC.

8. **PII minimization:** Logs **MUST NOT** dump full **payloads** of personal fields (names, phones, emails, free-text notes) by default; log **hashes or redacted previews** only if needed, per team policy — **US-B3** AC.

### Cross-cutting

9. **Primitives alignment:** Reuse **`src/features/ops/components/ops-primitives.ts`**, **`OpsLoadingRegion`**, and existing layout shell patterns where they already exist so **loading / error** UX stays cohesive — **[`docs/epic-11.md`](../epic-11.md)** §7.

10. **Realtime migrations:** If subscription channels require **Supabase Realtime** or publication changes, ship via **`supabase/migrations/`** only when **necessary** for **US-B2**; **do not** bundle unrelated RLS refactors (**E1** belongs in **11.1**).

### Implementation notes

- Prefer **one** client-visible error mapping function for **`useTransition` / `useActionState`** (or current project pattern) so **AC3** is enforced centrally.
- **Correlation:** Reuse **request headers** or **Next.js `headers()`** patterns the app already uses; if none, generate a **short request id** per action invocation and return it to the client in **safe** error payloads for support tickets.
- **Logging:** Use the project’s existing logger (`console` structured JSON in dev only vs production sink — follow repo conventions); **never** log **env secrets**.
- **Freshness:** When adding **“last updated”**, use **server clock** or **data `updated_at`** consistently; avoid misleading timestamps.
