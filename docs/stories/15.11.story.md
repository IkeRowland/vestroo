## Story

- As a **booker** (corporate or walk-in), I need **optional rider contact fields** (**name**, **phone**, **email**) on the **booking**, so that **ops and future notifications** can reach the **person actually travelling** for confirmations and (later) tokenised tracking — without requiring the rider to have a portal account (**Q21**).

## Acceptance Criteria (ACs)

1. **Database — nullable columns:** Add **`rider_name`**, **`rider_phone`**, **`rider_email`** to **`public.bookings`** as **nullable** **`text`** (or **`varchar`** consistent with neighbouring columns — **survey** existing `customer_*` column types) via a new migration under **[`supabase/migrations/`](../../supabase/migrations/)** with a clear **`epic15_15b1`** / **15B.1** comment. **Default** all **`NULL`** for backfill; **no** `NOT NULL` requirement.

2. **`live_rider_tracking` split (epic §8):** **Default:** **do not** add **`customer_accounts.live_rider_tracking`** in **15B.1** — defer to **15B.5** per epic catalogue. **Exception:** one migration file may add **only** a **`boolean default false`** column **without** any app read/write if the team agrees it reduces migration churn — document in **Progress Notes** and link **15B.5** as the story that **turns on** UI and reads the flag.

3. **PII / POPIA:** Treat rider fields as **personal information** — same retention and access discipline as **`customer_name` / `customer_email` / `customer_phone`** (minimise logging of values in **server** `console.*`; **no** new public APIs exposing rider fields without auth). Add a **short** note in **Progress Notes** or **Dev guidance** (not a legal doc).

4. **Forms — coverage:** **Survey** all **`bookings`** **INSERT** paths and add UI + payload wiring for **optional** rider fields where product needs them:
   - **Trip-request funnel:** **[`src/actions/submitTripRequest.ts`](../../src/actions/submitTripRequest.ts)** + **[`src/features/booking/components/trip-request/`](../../src/features/booking/components/trip-request/)** (e.g. **`trip-request-submit-schema.ts`**, slides / shell) — must support **account** and **walk-in** resolutions (**`clientTypeResolution`** / **`enrichTripRequestBookingWithClientType`**).
   - **Point-to-point / wizard flows:** **[`src/actions/createBooking.ts`](../../src/actions/createBooking.ts)**, **[`src/actions/processPayment.ts`](../../src/actions/processPayment.ts)** (and related steps), **[`src/features/booking/components/ContactDetailsForm.tsx`](../../src/features/booking/components/ContactDetailsForm.tsx)**, **`useBookingStore`** — **survey** **[`src/features/booking/`](../../src/features/booking/)** for any additional submit surfaces.
   - **Walk-in (Q20):** Walk-ins **do not** get a portal; they **may** still optionally provide **rider** contact on the **public** booking flow so a **future** SMS to rider (**US-C1**) is possible — fields remain **optional**.

5. **Labels / UX:** Clearly label fields as **“Rider / passenger contact (optional)”** (or equivalent) so bookers distinguish **rider** vs **booker** (**customer_***) contact. Empty submission = **`NULL`** in DB.

6. **Server validation:** Reuse or align with existing patterns: **email** — `z.string().email()` or trim + empty → `null`; **phone** — prefer **`libphonenumber-js`** / **`passengerPhoneToE164`** style where a country selector exists; for **simple** optional phone, **either** **light** validation (non-empty → basic format / length cap) **or** **strict E.164** consistent with **`trip-request-submit-schema`** — **pick one approach per funnel** and document in **Progress Notes**. **`rider_name`** — sensible max length (e.g. **≤ 200** chars) and trim.

7. **RLS — SELECT / UPDATE:** **Survey** existing policies on **`public.bookings`** (e.g. **`bookings_select`**, **`bookings_select_account_member`**, **`bookings_update`**, **`bookings_insert`**, chauffeur-linked selects from **[`supabase/migrations/`](../../supabase/migrations/)**). **AC:** New columns inherit the **same** row-level access as the rest of the **`bookings`** row (no **wider** exposure to **`authenticated`** than today). If any policy uses **explicit column lists** in tools/views, extend them. **Account-member `UPDATE`:** only add if product requires **post-create rider edits** in **15B.1** — otherwise **document** “create + staff ops only” and defer member **UPDATE** to a later story.

8. **Types / codegen:** Update **hand-maintained** booking row / insert shapes in **[`src/types/database.types.ts`](../../src/types/database.types.ts)** (see file header — **optional** full dump: **`npm run db:types`** → **`src/types/supabase.generated.ts`**, gitignored, for diff only). Fix compile errors in **`insert`/`update`** call sites; **survey** exact type names used for **`bookings`** (e.g. `BookingsRowDb` or table `Row`).

9. **Tests:** Add or extend **unit** tests for Zod / normalisation (e.g. next to **`trip-request-submit-schema.test.ts`** or **`ContactDetailsForm`** validation if extracted). **Manual:** one walk-in and one **account-linked** booking with rider fields populated + one with all rider fields empty. **No** full **15B.8** E2E.

10. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **Theme E `15B.1`**, **US-C1** data prerequisite (columns before **15B.2** token mint).
