## Story

- As **ops staff (dispatcher or admin)**, I need a **server action** to **mark EFT received** so walk-in bookings move from **`awaiting_payment`** to **`ready_to_assign`** and account bookings from **`invoiced`** to **`paid`**, with **`payment_status`**, receipt timestamp, and evidence reference persisted per **Q32**.

- As **engineering**, I need **strict validation**, **idempotent** re-submission when settlement is already recorded, and a **variance path** when the received amount differs from the expected quote/invoice amount by more than **R 0.01**, requiring **`varianceReason`** (min **10** characters) stored on the audit payload.

- As **compliance / audit**, I need every successful first-time mark to write **`ops_audit_log`** with **`action = 'payment_received_eft'`** and a payload including **`evidence_ref`**, **`amount_zar`**, **`prior_status`**, **`new_status`**, and when applicable **`variance_reason`**.

## Acceptance Criteria (ACs)

1. **Server module:** New file **`src/actions/markBookingPaymentReceived.ts`** exporting **`markBookingPaymentReceivedAction`** (or barrel name aligned with repo conventions — **one** public entry point) with input shape **matching** epic **US-N3**:
   ```ts
   {
     bookingId: string
     evidenceRef: string
     amountZar: number
     receivedAt: string // ISO timestamp
     varianceReason?: string // required when variance path triggers (see AC5)
   }
   ```
2. **Authorisation:** Caller must be **`dispatcher`** or **`admin`** (same pattern as other ops actions); otherwise return structured failure (e.g. **`forbidden`** / staff-only) — **no** raw role strings leaked to customers.
3. **Validation:**
   - **`bookingId`**: valid UUID; row **exists**; else reject.
   - **Status gate:** current **`bookings.status`** must be **`awaiting_payment`** (walk-in, `client_type = 'walk_in'`) or **`invoiced`** (account, `client_type = 'account_client'`); else reject with machine-stable reason (e.g. **`invalid_status_for_payment_mark`** per epic narrative).
   - **`amountZar`**: **> 0** (reject zero/negative).
   - **`receivedAt`**: **≤ now()** in the server’s authoritative clock (reject future-dated receipts).
   - **`evidenceRef`**: non-empty trimmed string within a **reasonable max length** (implementer picks limit, document in Progress Notes).
4. **Success side-effects (first application):**
   - Set **`bookings.payment_status = 'paid'`**, **`payment_received_at`** = parsed **`receivedAt`**, **`payment_evidence_ref`** = **`evidenceRef`**.
   - Transition **`bookings.status`**: walk-in **`awaiting_payment` → `ready_to_assign`**; account **`invoiced` → `paid`**.
   - Insert **`ops_audit_log`** row: **`action = 'payment_received_eft'`**, payload includes **`evidence_ref`**, **`amount_zar`**, **`prior_status`**, **`new_status`**, and optional **`variance_reason`** (snake_case keys in stored JSON **consistent** with existing audit payloads in repo).
5. **Variance check:** Compare **`amountZar`** to the story-implementer–verified **expected settlement amount** (see **Dev Technical Guidance** — **quote amount survey**). If **absolute difference > 0.01 ZAR**, require **`varianceReason`** with **`length >= 10`**; else reject. When variance path used, persist **`variance_reason`** on the audit payload.
6. **Idempotency:** If the booking **already** has settlement recorded ( **`payment_status = 'paid'`** and **`payment_received_at IS NOT NULL`** and status is already the **post-mark** terminal state for that workflow — walk-in **`ready_to_assign`**, account **`paid`** ), a subsequent call returns **`{ ok: true }`** (or equivalent success) with **no** second **`ops_audit_log`** row and **no** further status/`payment_*` mutation.
7. **UI (epic ~738–739):**
   - **Preferred:** **`MarkPaymentReceivedDialog`** (epic **§8**) opened from **`/ops/walk-in?stage=awaiting_payment`** and **`/ops/accounts?stage=invoiced`** row actions when those routes exist in the same PR.
   - **Alternative:** If routes absent, document **follow-up** wiring to **A1**/**A2** (story file IDs TBD) **or** interim wiring to **`/ops/bookings`** / **`/ops/fulfil`** **only with product approval** — captured as checked tasks in **Tasks** before marking story **Done**.
8. **Tests:** **`src/actions/__tests__/markBookingPaymentReceived.test.ts`** covers: happy path walk-in; happy path account; wrong status rejected; non-staff rejected; idempotent re-mark; variance requires reason; future-dated **`receivedAt`** rejected.

### Quote / invoice amount survey (variance baseline — AC5)

- **Walk-in (`client_type = 'walk_in'`, status = `awaiting_payment`):** authoritative amount = **`booking_quotes.total_zar`** of the row at `bookings.current_quote_id`; falls back to **`v_booking_current_quote.total_zar`** when `current_quote_id` is null **or** the row is missing (matches the existing `loadResolvedBookingQuoteForOps` contract in `src/lib/booking-current-quote.ts`).
- **Account (`client_type = 'account_client'`, status = `invoiced`):** authoritative amount = **`bookings.total_amount`** (the invoicing surface in `src/lib/ops-invoicing-queue.ts` already treats this column as the invoice total — `INVOICING_BOOKING_SELECT` selects `total_amount` and renders it in the invoicing queue UI). No separate invoice table exists yet.
- **No `bookings.payment_amount_zar`** column was found in repo (`grep -ri 'payment_amount_zar'` → 0 hits across `src/` + `supabase/migrations/`); the dev guidance hint about that column was conditional and is **not** the path taken.
- **Tolerance:** `Math.abs(amountZar - expected) > 0.01` triggers the variance branch (epic AC: *“variance > R 0.01”*).
- **Unknown expected amount path:** when neither side resolves a number (e.g. an account row with `total_amount = null`, or a walk-in with no quote rows at all), the action **does not** require `varianceReason` (no baseline ⇒ no variance gate). The audit payload still records `expected_amount_zar: null` + `expected_amount_source: 'unknown'` so finance can still reconcile post-hoc.

### Validation choices (AC3)

- **`evidenceRef`:** trimmed; min length 1; max length **200** chars (exported as `PAYMENT_EVIDENCE_REF_MAX_LENGTH`). Picked to match the bank-statement description practical ceiling (most banks cap free-text at ~140) and stay well clear of the `text` column / log fan-out.
- **`bookingId`:** `z.string().uuid()`.
- **`amountZar`:** `z.number().finite().positive()` — Zod rejects 0, negative, NaN, ±Infinity at the schema layer.
- **`receivedAt`:** parsed with `Date.parse`; rejected when `NaN` (`INVALID_RECEIVED_AT`) or strictly greater than `Date.now()` (`FUTURE_RECEIVED_AT`).
- **Status gate:** strict per epic — `awaiting_payment` for walk-in, `invoiced` for account; anything else returns `INVALID_STATUS_FOR_PAYMENT_MARK` (matches the epic narrative ‘`OpsActionError('invalid_status_for_payment_mark')`’).
- **Authorisation:** delegated to `getOpsStaffForAction` (dispatcher / admin only). Audit row stamps `actor_role = 'admin'` when caller is admin, else `'dispatcher'` (matches `OpsAuditActorRoleDb`).

### Idempotency (AC6)

- Early-return success when **all of**: `payment_status === 'paid'`, `payment_received_at !== null`, and the current `status` is the post-mark terminal state (`ready_to_assign` for walk-in, `paid` for account). No second `ops_audit_log` row is written; no further `bookings` mutation is attempted. Returns `{ ok: true, idempotent: true }` so callers (future dialog) can render an inert success without re-confirm UX.

### Single-mutation safety (AC4 — Task 0)

- Updates `bookings` in **one** `update().eq('id', …).eq('status', priorStatus).eq('client_type', …)` round-trip with `select('id').maybeSingle()` so a concurrent `cancel`/`assign` between the load and the write returns no row and the action surfaces `DATABASE` failure rather than silently writing a stale state. RLS still gates row visibility per Epic 12 / 14 policies; `revalidatePath` is fired only on first-time success.

### Audit payload (AC4)

- `action = 'payment_received_eft'`, `entity = 'booking'`, `entityId = bookingId`, snake-case payload keys: `evidence_ref`, `amount_zar`, `prior_status`, `new_status`, `received_at`, `expected_amount_zar`, `expected_amount_source`, `client_type`, and (variance branch only) `variance_reason`. Aligns with the existing `appendOpsAuditLog` writer in `src/lib/ops-audit.ts`.
