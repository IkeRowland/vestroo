# Story 10.6: Public trip-request funnel — post-implementation hardening & ship readiness

## Status: Done

**Dependencies:** **[`docs/epic-10.md`](../epic-10.md)** — **FE.10.1–FE.10.6** behaviour is implemented and design-aligned; this story does **not** add a new **FE** requirement from the epic text (no **FE.10.7**). **Related NFRs:** **NFR.1.1** (performance), **NFR.3.1** (security / TLS), **NFR.3.2** (SEO / routing patterns where the booking entry is marketed). **Prerequisites — funnel + docs assumed ready for hardening:** **[`docs/stories/10.1.story.md`](10.1.story.md)** through **[`docs/stories/10.4.story.md`](10.4.story.md)** (functional **FE.10.1–FE.10.5**). **[`docs/stories/10.5.story.md`](10.5.story.md)** (**FE.10.6** alignment + integration-boundary doc). **Story 10.6** owns automated test coverage, repeatable accessibility verification, performance / NFR documentation, and optional documentation parity deferred from **10.5** — not new product scope.

**Explicit out of scope:** New product features. PayFast, instant pricing, quote totals, or fare assertions in tests. Ops console features. Automated client email for quote/payment-link. New application routes for funnel steps (**FE.10.1** remains one primary page). Rebuilding UI except minimal `data-testid` / accessibility hooks only where tests or a11y verification require stable selectors. Large new dependencies without brief justification in Tasks / PR (performance tooling included).

**Constraining NFRs:**

- **NFR.1.1 (Web performance — [`docs/epic-10.md`](../epic-10.md)):** Hardening SHOULD document a baseline or budget for the trip-request route; MUST NOT trade large regressions in CLS / blocking scripts for convenience without recording the trade-off.
- **NFR.3.1 (Security):** Tests and docs MUST assume HTTPS; MUST NOT add mixed-content URLs or weaken TLS assumptions for local E2E without documented mitigation.
- **NFR.3.2 (SEO):** If verification touches metadata or entry from marketing pages, preserve existing ISR / routing patterns per epic — Related Non-Functional Requirements.

## Story

- As a maintainer shipping the public trip-request funnel and as a traveler relying on accessible, stable behaviour
- I want automated tests, repeatable accessibility checks, and documented performance expectations for `/book/trip-request` (and embedded shell usage if in scope for tests), plus optional documentation parity with [`docs/epic-10.md`](../epic-10.md#relationship-to-epic-1-dependency--conflict) when Story 10.5 deferred it
- so that **FE.10.1–FE.10.5** regressions are caught early, keyboard / screen-reader paths stay verifiable, **NFR.1.1** has a stated baseline or budget, and epic-1 wording does not silently contradict Epic 10 where product opts in

## Acceptance Criteria (ACs)

### Automated testing — Vitest (unit / logic)

1. **Schema and validation coverage:** Vitest tests MUST cover or extend coverage for public trip-request logic aligned with **FE.10.2–FE.10.5**, including at minimum integration with existing files under `src/features/booking/components/trip-request/` (for example `trip-request-submit-schema`, `ride-details-validate`, `trip-offer-vehicle`). Gaps identified in Dev Technical Guidance MUST be closed or explicitly waived with reason in Tasks.

2. **Shell / slide behaviour (where unit-testable):** Where feasible without heavy new machinery, add tests for deterministic helpers or pure functions used by `TripRequestBookingShell` and slides (for example prefill parsing, step gating, validation branches) — prefer extending existing patterns in `__tests__/` adjacent to trip-request modules.

3. **No pricing / PayFast assertions:** New tests MUST NOT assert rand pricing, PayFast flows, quote totals, or payment checkout on the trip-request funnel — guardrails consistent with [Non-Goals](../epic-10.md#non-goals).

### Automated testing — Playwright (E2E)

4. **Happy path — trip-request entry:** Playwright spec(s) under `tests/e2e/` MUST cover a stable happy path for the public trip-request funnel starting from `/book/trip-request` or the documented bootstrap path (for example prefill via `/book/search` then navigation to `/book/trip-request` if required by implementation — discover and document the chosen flow in Dev Technical Guidance). MUST reach successful submission or the documented “request received” outcome without PayFast.

5. **Validation / error paths:** At least one E2E scenario MUST exercise a representative validation failure or blocked progress (for example required fields, missing vehicle selection, invalid passenger input) consistent with **FE.10.2–FE.10.4** — without depending on pricing APIs.

6. **Selectors and stability:** E2E tests SHOULD prefer accessible roles / labels; MAY add minimal `data-testid` only where needed for stability (in scope per Explicit out of scope exception).

### Accessibility verification

7. **Repeatable posture:** The repo MUST document one repeatable approach for funnel accessibility verification: either (a) automated lint via existing `eslint-plugin-jsx-a11y` coverage on relevant files (see `eslint.config.mjs`), or (b) a short manual checklist checked in PR for this story, or (c) optional `@axe-core/playwright` (or similar) only if added with justification and minimal footprint — pick at least one primary method and state it in Testing / verification.

8. **Keyboard path documented:** Testing / verification section MUST document a keyboard-only path through the full `TripRequestBookingShell` flow (all in-page steps defined by the shell — see Dev Technical Guidance for `STEP_COUNT` / prefill semantics) including focus movement across steps and submit / request-received outcome.

### Performance — NFR.1.1

9. **Baseline or budget:** MUST add documentation (for example in `docs/` or Story Progress notes linked from Dev Technical Guidance) recording either (a) a one-time Lighthouse or Web Vitals snapshot from a preview / local production build, or (b) explicit performance budget targets (for example LCP / CLS thresholds) for `/book/trip-request` — reasonable effort; no mandatory new CI pipeline unless already aligned with repo practice.

10. **Dependencies:** New performance or a11y npm packages are optional and require one-line justification each in Tasks.

### Optional documentation parity (Story 10.5 deferrals)

11. **(Optional)** **`docs/epic-1.md`:** If Story 10.5 deferred [Recommendation (a)–(b)](../epic-10.md#relationship-to-epic-1-dependency--conflict), MAY complete minimal supersede / pointer language so **FE.1.1–FE.1.4** public funnel wording does not contradict Epic 10 — product approval required before merge.

12. **(Optional)** **`docs/core-traveller-flow-parity.md`:** MAY apply minimal edits so search → quote → PayFast language does not contradict Epic 10 — same approval rule as AC11.
