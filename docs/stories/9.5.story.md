## Story

- As a **product, finance, ops, compliance, and engineering** stakeholder with **go** at **[`#sh-9-1`](../epic-9.md#sh-9-1)** and **SH.9.2–SH.9.4** baselines (**domain**, **capacity**, **live ops**) in place
- I want **booking and payment** rules for **patterned / capacity-managed** products **specified and implementable** (vs on-demand **[VST-6](vst-6.story.md)**), including **refund** and **no-show** behaviour, with **PayFast** (or **product-approved** provider) **following** **[INT.8.3](../integrations-and-payments.md#int-8-3)** and existing **webhook idempotency**
- so that **customers** can complete **patterned** checkout **without** inventory contradictions, **finance** has clear **refund / no-show** rules, and **engineering** does not fork **payment authority** away from **documented** PayFast **ITN** semantics

## Acceptance Criteria (ACs)

### Gate and prerequisites

1. **Gate compliance:** No implementation merging **SH.9.5** behaviour (checkout paths, **Server Actions**, **webhook** branches, **booking** / **ticket** status transitions, or **RLS** for payment-adjacent rows **specific to patterned / capacity**) unless **[`docs/epic-9.md#sh-9-1`](../epic-9.md#sh-9-1)** records **go**. If **no-go** or unset for implementation, outcome is **N/A — not executed** (same spirit as **SH.9.4** **AC1**).

2. **Prerequisite traceability:** PR description and story footnotes **MUST** cite **[`docs/stories/9.1.story.md`](9.1.story.md)** through **[`docs/stories/9.4.story.md`](9.4.story.md)**, **[`docs/adr/0002-patterned-shuttle-domain-sh9-2.md`](../adr/0002-patterned-shuttle-domain-sh9-2.md)**, **[`docs/adr/0003-service-run-capacity-holds-sh9-3.md`](../adr/0003-service-run-capacity-holds-sh9-3.md)**, and **[`docs/adr/0004-patterned-run-realtime-sh9-4.md`](../adr/0004-patterned-run-realtime-sh9-4.md)** when claiming **SH.9.5** scope.

### Product rules and documentation (when **go**)

3. **VST-6 delta (documented):** Deliverable **MUST** state how **patterned / capacity** checkout **differs** from on-demand **[VST-6](vst-6.story.md)** flows — at minimum: **when** a **`service_run`** (or agreed **ADR 0002** key) attaches to a **booking** / **ticket**; **how** quotes interact with **per-run** capacity; **customer-visible** steps (hold → pay → confirm vs **VST-6** happy path). **MUST** cite **[`docs/front-end-api-interaction.md`](../front-end-api-interaction.md)** where **Server Actions** or **API** contracts change.

4. **Capacity ↔ payment handoff:** Rules **MUST** describe **hold → payment → confirmed occupancy** (or **explicit** alternative) **without** contradicting **ADR 0003** — including **what** happens to **holds** on **payment timeout**, **failed** / **cancelled** PayFast **ITN** (align with **[`docs/integrations-and-payments.md`](../integrations-and-payments.md)** **PayFast webhook lifecycle**), and **idempotent** retries (**AC** parity with **SH.9.3** **AC6** intent).

5. **INT.8.3 compliance (by reference):** **PayFast** (or **approved** provider) **MUST** follow **[INT.8.3](../integrations-and-payments.md#int-8-3)** — **link** **`#int-8-3`** and the **PayFast webhook lifecycle** subsection; **state** any **new** branches (e.g. **patterned** booking rows) **only** as deltas **on top of** documented **ITN** / **signature** / **duplicate `COMPLETE`** behaviour — **no** parallel “shadow” payment confirmation path.

6. **Refund rules:** **Product-approved** rules for **customer** and **staff-initiated** refunds (or **honest** **TBD** + **manual** ops posture where automation does **not** exist) **MUST** be written — including **effect on** **`tickets`** / **`trip_seats`** / **capacity** (**release** vs **block**), **timeline** vs **run** **`scheduled_start`**, and **alignment** with **INT.8.3** matrix **refunds** row (**reference** vs **Vestroo** **gap** honesty).

7. **No-show rules:** **Product-approved** **no-show** definition and **operational** outcome **MUST** be specified (e.g. **forfeit**, **partial** credit, **manifest** / **ops** marking) — **without** contradicting **manifest** / **RLS** expectations (**VST-12**, **ADR 0002**).

8. **Data model alignment:** **[`docs/data-models.md`](../data-models.md)** (and **`src/types/database.types.ts`** if schema changes) **MUST** reflect any **new** statuses, **FKs**, or **flags** for **patterned** checkout — **no** silent drift vs **bookings** payment fields documented in **VST-13** / **INT.8.3**.

9. **Epic / integrations index:** If new normative prose lands outside **`integrations-and-payments.md`**, **MUST** add **cross-links** so readers reach **SH.9.5** rules within **≤2 clicks** from **[`docs/epic-9.md`](../epic-9.md)** and/or **[`docs/integrations-and-payments.md`](../integrations-and-payments.md)** (maintainer choice — **one** canonical spec home + **short** pointers elsewhere).

10. **Tests / verification:** Automated or **documented** staging checks for **patterned** checkout — **minimum**: **hold + pay** does **not** double-consume capacity; **failed** payment leaves **consistent** **`bookings`** / **ticket** state per **INT.8.3** + **integrations** doc; **duplicate** **`COMPLETE`** **ITN** remains **idempotent**.
