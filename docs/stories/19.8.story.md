## Story

- As **a traveler on slide 3**, I see a **non-blocking** notice when my **email domain** matches a **known corporate account**, so I understand how the booking may be associated **without** a modal interrupting the flow (**FE.19.8**).
- As **a traveler with multiple matching orgs**, I can **pick the correct org** using **radio chips** with a **sensible default** (first match), or dismiss to **book as a guest** where the product allows.
- As **ops / data integrity**, I need the same **`clientTypeResolution`** payload rules and server-side inference as today (**Epic 12**, **NFR.19.6**).

## Acceptance Criteria (ACs)

1. **No mid-flow modal (trip-request slide 3):** Corporate domain match UI is **inline** on **slide 3** (below the email field in the passenger column), not a **`fixed inset-0`** blocking dialog (**remove** modal overlay pattern from this flow for **`TripRequestBookingShell`** usage).

2. **Copy & structure:** When probe finds **≥1** org, show inline text recognising **{domain}** / **{Org Name}** per product copy (epic template: “We recognise {domain} as {Org Name}…”); show **dismiss** control labelled per product (e.g. **“Book as a guest instead”**) that applies the same resolution outcome as today’s **“No, personal booking”** path (**`walk_in`** + **`user_declined_domain_match`**).

3. **Multiple orgs:** **≥2** candidates → **radio chips** (not only a `<select>`); **default selection = first match**; changing chip updates **`clientTypeResolution`** / invoicing context the same way choosing a different account would today.

4. **Submit never blocked by notice:** With valid **`fullSubmitParsed`** and **PO** rules satisfied, **Submit** runs **`submitTripRequest`** even if the user **never** opened or dismissed the notice (no **`ensureReadyForSubmit`** failure path for “unconfirmed modal” on this funnel).

5. **`clientTypeResolution` payload behaviour unchanged:** For equivalent user actions (confirm org, dismiss, no match, probe error), the **`clientTypeResolution`** object attached to **`tripRequestSubmitPayloadSchema`** / **`submitTripRequest`** matches **pre-19.8** semantics (field names, **`clientType`**, **`clientTypeSource`**, **`customerAccountId`** presence rules).

6. **Accessibility:** Inline region is keyboard operable (**NFR.19.2**); chips / dismiss have visible labels; loading / error text for domain probe remains sensible (**`aria-live`** where appropriate).

7. **Tests:** Update or add RTL / integration coverage for **inline** notice, **multi-org** chips, **dismiss**, and **submit** without modal; **`BookingAccountDomainGate`** tests if present, plus **`TripRequestBookingShell.vehicle-gate.test.tsx`** (currently mocks gate as **`null`** — extend or add dedicated suite for **19.8**); **`npm run test`** / **`npm run lint`** green for touched suites.
