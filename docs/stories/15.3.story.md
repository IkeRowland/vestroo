## Story

- As an **account user**, I need a **real, paginated bookings list** at **`/account/bookings`** for my **active** organisation, with **sort**, **filters**, and **row navigation** to a detail route, so that I can see **past, current, and upcoming** trips in one place **without calling ops** (per **US-A2**).

## Acceptance Criteria (ACs)

1. **Replaces 15A.2 stub:** **`src/app/(account)/account/(portal)/bookings/page.tsx`** is no longer a thin "ships in 15A.3" placeholder only. It implements a **server-rendered** list of bookings for the **active** `customer_accounts` context, with **server-side** membership checks consistent with **15.1** / **15.2** and **RLS** aligned to the same invariants (no cross-account ids in queries).

2. **Pagination:** The list is **paginated** (page size **survey** — e.g. align with ops patterns or a sensible default such as 20–50). **Page / cursor** may be URL-driven (`?page=` or `?cursor=`) or an equivalent **server-friendly** pattern documented in **Progress Notes**.

3. **Sort (pickup date):** Default sort is **pickup datetime** (direction **survey** product preference — e.g. **ascending** for "soonest first"). The UI exposes **sort controls** to toggle **ascending / descending** by pickup (labels clear to the user). Sort state is reflected in the URL or another shareable, bookmarkable pattern.

4. **Row columns (US-A2):** Each row shows, **when present in the schema**: **booking reference** (e.g. `payment_reference` or agreed canonical ref field — **survey** `bookings` + joins), **pickup datetime**, **route** as **origin → destination** (e.g. `origin_name` / `destination_name` or trip-derived labels — **survey**), **vehicle category** (e.g. from trip/vehicle category join — **survey**; if the schema only exposes vehicle name, show that and document the gap in **Progress Notes**), **status** as a **badge** (map `bookings.status` to readable copy), **total amount** (e.g. `total_amount` formatted), **payment status** (e.g. `payment_status`). If any column is missing in DB, **do not invent** data — use **"—"** and note the gap.

5. **Filter chips (US-A2):**
   - **Status — multi-select** (whitelist values consistent with `bookings.status` / product needs; follow **ops** style where helpful — repeat keys or comma lists — see **`parseOpsBookingsQueueSearchParams`** patterns in `src/lib/ops-bookings-queue-query.ts`).
   - **Intent** — filter by `bookings.booking_intent` (include null/unset if the ops grid supports an `_null`-style value — **survey** `OpsBookingsQueueIntent` / `formatBookingIntentLabel`).
   - **Time window:** **next 7d**, **next 30d**, **past 90d**, **all** — implemented as **predicates** on `pickup_datetime` (or agreed canonical pickup field) in the **active-account** query.
   - Filter state is **URL-backed** (`searchParams`) in a way **consistent** with **`/ops/bookings`** precedence where practical (new keys are fine; document chosen param names in **Progress Notes**).

6. **Query scope:** All list queries **filter by** `bookings.customer_account_id = activeAccountId` (or equivalent **verified** join) in addition to **RLS** — **double defense** as in other portal read paths. Do **not** pass account id from the client.

7. **Row navigation:** Each row is a **link** (or row click → navigate) to **`/account/bookings/[id]`** with the booking’s **`id`**. **15A.4** full detail, quote line items, and artefacts are **out of scope**; **AC for this story:** the **`[id]`** route **exists**, returns **200** with a **thin placeholder** (copy citing **15A.4**), and returns **403** (or project-standard forbidden pattern) / **not found** when the booking is **not** part of the active account or is **invisible** under RLS. **No** 404 for valid in-scope rows when the user is an authorised member of the account.

8. **"New booking" (US-A2 prefill) — product split:** A **"New booking"** (or equivalent) CTA is visible on the list page and links to the **public** booking entry (**survey:** **`/book/search`** as in **15.2**). **Prefill** of the **default PO** (when `default_po_required` / account default PO policy applies) and **member email** per US-A2 last bullet:
   - **(B) Chosen for 15A.3 (survey result):** The current **`/book/search`** page only types `searchParams` for `{ tab?: string }` in **`src/app/(app)/book/search/page.tsx`**; **`BookingSearchForm`** does not consume PO/email from the URL. **Therefore** the **full** US-A2 prefill behaviour is **deferred** to a **follow-on** (define a short title in **Progress Notes**, e.g. *Portal booking prefill / US-A2b*) with a **spike** task: **query-param contract** vs **sessionStorage bridge** (see `trip-request-prefill` patterns) vs **server session**. **In scope for 15A.3 DoD:** the CTA and link to `/book/search` only, unless the same PR **explicitly** extends the public funnel (out of the minimal list scope — optional stretch, not required for 15A.3 completion).

9. **UI cohesion:** Reuse **account portal** layout from **15.1/15.2**; table/chips/cards should align with **ops** list UX where reasonable (`OpsTableShell`-style patterns **optional** — avoid importing ops-only chrome if it couples layouts; **prefer** `src/features/account/components/` or shared primitives).

10. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **US-A2** list bullets; catalogue **15A.3**; defers full **US-A2** row-click **detail** content to **15A.4** and **US-A2** **prefill** follow-on per **AC8 (B)**.
