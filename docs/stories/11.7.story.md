**Constraining principles (from epic Themes H & I):**

- **Funnel parity:** Tour package selection behaves like an established booking slide (**progress**, **validation**, **back/next**) comparable to **`TripRequestVehicleSlide`**; selected package **binds** to checkout metadata for **`experience_package`** intent.
- **Shuttle-grade contact:** Contact capture uses **`ContactDetailsForm`** (or a documented successor) **after** the agreed step order; validation and errors match existing booking forms; persisted data satisfies the **`experience_package`** contract on **`bookings` / `booking_metadata`**.
- **Intent integrity:** **`experience_package`** flows through quote, store, and **payment/processing** consistently with **`booking-schemas`** and **`processPayment`** (and related tests).
- **Ops truth:** Staff can **list, create, edit, deactivate/archive** `experience_packages` per schema; mutations are **RLS-safe**; public/marketing tour surfaces reflect changes within **cache / revalidate** expectations documented for those routes.

## Story

- As a **customer** booking a **tour / experience package**
- I need a **package selection step** with **progress**, **validation**, and **back/next** behaviour **consistent with** the trip-request slide model (**`TripRequestVehicleSlide`**)
- so that I can **choose a package confidently** and have that choice **bound** to checkout metadata for **`experience_package`** intent — **US-H1**

- As a **shuttle-style customer** (or any customer using the tour funnel after package selection)
- I need **contact details** captured via **`ContactDetailsForm`** (or successor) **in the correct order** relative to other steps
- so that **validation and errors** match existing booking forms and my details land in **`bookings` / `booking_metadata`** per the **`experience_package`** contract — **US-H2**

- As **product / engineering**
- I need **`experience_package`** intent wired **end-to-end** through **payment and processing** where the product today expects intent + metadata
- so that **quotes, creates, and PayFast (or successor) paths** remain consistent with **`booking-schemas`** / **`processPayment`** and do not regress other intents — **US-H3**

- As **ops staff**
- I need **CRUD for `experience_packages`** on **`/ops/experiences`** (list, create, edit, deactivate/archive per schema)
- so that **catalogue and pricing-facing fields** stay accurate and changes become **visible** on public tour flows within agreed **cache/revalidate** behaviour — **US-I1**

## Acceptance Criteria (ACs)

### US-H1 — Package selection slide; trip-request parity; metadata binding (Theme H)

1. **Slide/shell parity:** The tour funnel **MUST** expose a **package selection** step whose **progress indicator**, **field/step validation**, and **back / next** controls are **comparable** to **`TripRequestVehicleSlide`** within **`TripRequestBookingShell`** (see **`src/features/booking/components/trip-request/TripRequestVehicleSlide.tsx`**, **`src/features/booking/components/TripRequestBookingShell.tsx`**) — **US-H1** AC.

2. **Selection → checkout binding:** The customer’s **selected experience package** (id/slug and any agreed display fields) **MUST** be stored in client booking state and carried into **quote / details / payment** such that **`booking_intent`** remains **`experience_package`** and **`booking_metadata`** satisfies the **`experience_package`** shape expected by **`src/actions/booking-schemas.ts`** and consumers of **`src/lib/experience-package-data.ts`** — **US-H1** AC.

### US-H2 — Contact details; order; persistence contract (Theme H)

3. **Flow order:** **`ContactDetailsForm`** ( **`src/features/booking/components/ContactDetailsForm.tsx`** ) or a **successor** documented in **Tasks** **MUST** run **after** the **package selection** (and any intermediate steps product defines), matching the **shuttle / trip-request** mental model — **US-H2** AC.

4. **Validation & persistence:** Form validation, error surfacing, and server-side rejection behaviour **MUST** align with existing app booking forms (e.g. **`src/app/(app)/book/details/page.tsx`** patterns). Submitted data **MUST** persist on **`bookings`** and **`booking_metadata`** per the **`experience_package`** contract used by **`src/actions/createBooking.ts`** / **`processPayment.ts`** — **US-H2** AC.

### US-H3 — Intent end-to-end in payment/processing (Theme H)

5. **Schema alignment:** **`experience_package`** payloads **MUST** validate through the same **Zod** contracts as other web bookings where applicable (**`src/actions/booking-schemas.ts`**); any new fields **MUST** extend schemas **without** breaking existing intents — **US-H3** AC.

6. **Processing:** **`src/actions/processPayment.ts`** **MUST** accept and persist **`experience_package`** bookings consistently with metadata rules already implied by **`createBooking`** / **`calculateExperienceQuote`** / **`src/lib/experience-package-data.ts`**; add or extend **automated tests** (e.g. alongside **`src/actions/__tests__/processPayment.test.ts`**, **`src/actions/__tests__/booking-schemas-experience.test.ts`**) so regressions are caught — **US-H3** AC.

### US-I1 — Ops CRUD; visibility on public flows (Theme I)

7. **CRUD surface:** Staff **MUST** be able to **list**, **create**, **update**, and **deactivate or archive** (per **`public.experience_packages`** schema in **`supabase/migrations/20260410120000_vst10_experience_packages.sql`** and any follow-on migrations) from **`/ops/experiences`** — **US-I1** AC. **Note:** Today’s **`src/app/(ops)/ops/experiences/page.tsx`** is a **read-only** experience **bookings** list; **11.7** extends or replaces sections of this route **only** as agreed in **Tasks** (e.g. sub-routes vs tabs) while preserving **Theme B** primitives already used there.

8. **Theme B on ops:** New or extended Experiences admin UI **MUST** use **`OpsFetchErrorIsland`**, **`OpsDataFreshnessBar`**, and loading patterns per **[`docs/stories/11.2.story.md`](11.2.story.md)** — **US-I1** / Theme B.

9. **Structured logging:** Mutating server actions for packages **MUST** emit **structured** logs per [`docs/ops-server-action-logging.md`](../ops-server-action-logging.md) (action name, outcome, safe ids) — **US-I1** / Theme B reinforcement.

10. **Public visibility:** After ops changes, **marketing tour pages** (e.g. **`src/app/(marketing)/tours/page.tsx`**, **`src/app/(marketing)/tours/[slug]/page.tsx`**) and the **booking panel** (**`src/features/booking/components/ExperiencePackageBookPanel.tsx`**) **MUST** show updated package data within **Next.js cache / `revalidatePath` / `revalidateTag`** expectations documented in **Tasks** or **`docs/ops-data-freshness.md`** if behaviour changes materially — **US-I1** AC.

### Cross-cutting

11. **RLS / smoke:** Any new **INSERT/UPDATE** policies for **`experience_packages`** (or related tables) **MUST** ship via **`supabase/migrations/`** and stay covered by **`supabase/smoke_rls.sql`** when staff roles change — cross-cutting with **11.1**.

12. **Schema verification:** Before locking implementation, **MUST** confirm **actual** columns and enums on **`experience_packages`** and how **`calculateExperienceQuote`** (**`src/actions/calculateExperienceQuote.ts`**) reads package rows — **cross-cutting** (avoid assuming fields absent in DB).
