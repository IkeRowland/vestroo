**Constraining principles (from epic Theme D):**

- **Table-first discovery:** **`/ops/search`** becomes a **searchable booking table** as the **primary** staff path; the legacy **form-only** flow (**`BookingSearchForm`**) may remain as a **secondary** entry (e.g. collapsed panel, tab, or deep link) but **must not** be the only way to discover bookings at scale.
- **Large datasets:** **Sort** and **pagination** (offset/limit **or** cursor — **pick one** in implementation and **document**) **must** be **normative** for the grid query, not ad-hoc “load all”.
- **Row actions:** Prefer **existing** routes and server flows (**modify booking**, **detail**) already used by staff; **no** new ops routes unless this story **explicitly** adds them in **Tasks** with PO sign-off.
- **Intent:** **`booking_intent`** is **visible** and **labelled** consistently with **fulfil** and **search**; values come from **`bookings.booking_intent`** (canonical DB column) **or** a **documented** derivation (if any) — **no** hidden client-only intent.

## Story

- As **ops staff**
- I need a **searchable booking table** (not a **form-only** primary flow) with **agreed minimum search fields**, **sort**, and **pagination/cursor** behaviour
- so that I can **find bookings quickly** at volume — **US-D1**

- As **ops staff**
- I need **columns, filters, and row actions** aligned with daily dispatch and support tasks (**status**, **intent**, **dates**, **route summary** — exact set **agreed** in implementation)
- so that I can **scan, narrow, and open** the right booking without redundant navigation — **US-D2**

- As **ops staff**
- I need **`booking_intent`** visible in **search results** and in **other ops booking lists** with labels **consistent** with fulfil/search
- so that I **interpret** shuttle, trip request, experience, and standard flows the same way everywhere — **US-D3**

## Acceptance Criteria (ACs)

### US-D1 — Searchable table; minimum fields; sort; pagination (Theme D)

1. **Table-first `/ops/search`:** **`src/app/(ops)/ops/search/page.tsx`** **MUST** present a **booking results grid** (table or agreed data-grid) as the **primary** discovery UX after search — **[`docs/epic-11.md`](../epic-11.md)** Theme D (**US-D1**). Wrapping **`BookingSearchForm`** from **`src/features/booking/components/BookingSearchForm`** **only** is **not** sufficient as the **sole** discovery path once this story ships.

2. **Minimum search fields (product-locked in PR):** The team **MUST** **document** the **exact** filter set for v1; **baseline expectation** from the epic is at least **reference** (e.g. `payment_reference` / reservation id), **contact** (e.g. phone/email — match strategy **documented**), and **pickup / created date range** (field(s) and timezone **named**). Deviations (e.g. drop email v1) **MUST** be **explicit** in the same doc/PR comment — **US-D1** AC.

3. **Sort:** Staff **MUST** be able to **sort** the grid by at least **one** business-meaningful column (e.g. pickup datetime, created_at, payment_reference) with **default sort** defined — **US-D1** AC.

4. **Pagination or cursor:** For large result sets, the implementation **MUST** use **either** offset/limit **or** cursor-based paging with **page size**, **max pages** (if any), and **stability** rules (e.g. sort tie-breaker by `id`) **documented** in [`docs/ops-data-freshness.md`](../ops-data-freshness.md) or a **one-line** pointer from that doc to a colocated module comment — **US-D1** AC.

### US-D2 — Columns, filters, row actions (Theme D)

5. **Column set:** The grid **MUST** expose an **agreed** column set including at minimum **status**, **`booking_intent`** (or its display column), **key date(s)** (e.g. pickup), and a **route summary** (origin/destination short string or agreed substitute from existing booking fields) — **US-D2** AC. Exact headers and empty-cell behaviour **as agreed** with PO.

6. **Filters beyond search box:** Staff **MUST** be able to narrow results with **filters** aligned to daily tasks (e.g. status, payment_status, intent — **subset agreed** in PR); filter predicates **MUST** match the server query (no client-only fake filtering of paged data) — **US-D2** AC.

7. **Row actions → existing flows:** Row actions (links/buttons) **MUST** route to **existing** staff/customer booking flows (**modify**, **details**, or current ops entry points used today from **`BookingSearchForm`** / booking app routes) **unless** this story’s **Tasks** record **new** routes with PO approval — **US-D2** AC.

### US-D3 — `booking_intent` visibility and canonical sourcing (Theme D)

8. **Search grid intent:** **`booking_intent`** **MUST** appear as a **dedicated column or badge** in the **`/ops/search`** results grid with **human-readable labels** — **US-D3** AC.

9. **Other ops booking lists:** Verified **`bookings`**-backed ops surfaces today: **`src/app/(ops)/ops/fulfil/page.tsx`** (via **`AssignBookingPanel`** / **`FulfilPanelBookingRow`**), **`src/app/(ops)/ops/experiences/page.tsx`**. Where these UIs list **booking rows**, they **MUST** show the **same** intent labels as the search grid (shared helper or enum map **required**) — **US-D3** AC.

10. **Canonical source:** Intent values **MUST** be read from **`bookings.booking_intent`** in Supabase/Postgres queries **or**, if displayed value is **derived**, the derivation **MUST** be **documented** next to the mapper (e.g. “null → Standard”) and **approved** — default is **no silent derivation** — **US-D3** AC.

### Cross-cutting

11. **Ops shell primitives:** The evolved **`/ops/search`** page **MUST** use **`OpsPageHeader`**, **`OpsFilterRow`**, **`OpsTableShell`** (or composition thereof), **`OpsDataFreshnessBar`**, **`OpsFetchErrorIsland`**, **`OpsEmptyState`**, and **`OpsErrorState`** from **`src/features/ops/components/`** consistently with **[`docs/stories/11.2.story.md`](11.2.story.md)** — **Theme B** consumption.

12. **Server actions / loaders:** Prefer **server components + Supabase** (`createUserServerClient`) for the grid query; any **new** **`src/actions/ops*.ts`** (or extension of existing **`searchBooking`** pattern) **MUST** follow structured logging from [`docs/ops-server-action-logging.md`](../ops-server-action-logging.md) and safe error shapes — **no** raw internals to the client.

13. **Freshness:** Update or annotate [`docs/ops-data-freshness.md`](../ops-data-freshness.md) for **`/ops/search`** with the **pagination**, **refetch**, and **stale** behaviour after mutations (e.g. **`router.refresh()`** if RSC-per-navigation).
