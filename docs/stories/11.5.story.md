## Story

- As **ops leadership**
- I need a **dashboard** with a **finite** set of **KPIs** for **operational health**, each with **documented** definitions (**numerator**, **denominator**, **timezone**)
- so that I can **scan health at a glance** and **trust** what each number means — **US-E1**

- As **ops staff**
- I need **drill-downs** from **each** KPI to a **filtered list** or **detail** view
- so that I can **investigate** the underlying bookings/trips **in context**, or see a **clear “no data”** explanation when nothing matches — **US-E2**

## Acceptance Criteria (ACs)

### US-E1 — Dashboard; finite KPIs; documented definitions; Theme B UX (Theme E)

1. **Dashboard surface:** Staff **MUST** reach a **dashboard** view via an agreed route (see **Tasks** — e.g. **`/ops`**, **`/ops/dashboard`**, or **PO-approved** evolution of **`/ops/board`** entry) that presents **all v1 KPIs** on one screen (or **documented** tabbed layout if PO splits sections) — **[`docs/epic-11.md`](../epic-11.md)** Theme E (**US-E1**).

2. **Finite KPI list:** The implementation **MUST** ship a **fixed, versioned** set of KPIs for v1 (no open-ended plugin list); the **exact** KPI keys/names **MUST** be listed in a **normative** doc or module comment block agreed in the PR — **US-E1** AC.

3. **Definitions doc:** For **each** KPI, the team **MUST** document **numerator** (query or rule), **denominator** (or explicit **“none”** / population definition), and **timezone** used for any **calendar** or **“today”** boundary — **US-E1** AC. Default expectation: **one** small artefact under **`docs/`** (e.g. **`docs/ops-dashboard-kpis-v1.md`**) **or** a colocated **`src/lib/ops-dashboard-kpis.md`** — **pick one** in **Tasks** and **link** it from [`docs/ops-data-freshness.md`](../ops-data-freshness.md) **if** freshness behaviour for the dashboard is non-obvious.

4. **Loading and errors:** The dashboard **MUST** use **`OpsLoadingRegion`** (or equivalent loading skeleton pattern already used on ops surfaces) for **initial** and **refetch** loading states where data is fetched client-side; **server** load failures **MUST** surface through **`OpsFetchErrorIsland`** wrapping **`OpsErrorState`** (or the **current** **11.2** composition); **MUST** include **`OpsDataFreshnessBar`** (or **documented** exception in [`docs/ops-data-freshness.md`](../ops-data-freshness.md) with rationale) — **US-E1** AC, **Theme B** alignment per **11.2**.

5. **No secret leaks:** User-visible error copy **MUST NOT** expose raw stack traces, JWTs, keys, or full SQL — **US-E1** / **Theme B** safety bar.

### US-E2 — Drill-downs; correct filters; empty states with reason (Theme E)

6. **Per-KPI drill affordance:** **Each** v1 KPI **MUST** expose a **primary** drill affordance (card link, “View” control, or entire card hit target per a11y review) that navigates to a **target route** recorded in the KPI definitions doc — **US-E2** AC.

7. **Filtered landing:** On navigation, the **target** page **MUST** apply **filters equivalent** to the KPI definition (e.g. same date window, status subset, bucket tab, search query params) **or** the KPI doc **MUST** state **why** an exact filter cannot be expressed and instead document the **closest** supported contract (requires PO sign-off) — **US-E2** AC.

8. **No-data UX:** If the drill lands on a **list** with **zero** rows **while the KPI was non-zero** (stale snapshot) **or** the KPI was **zero** and staff still navigated, the UI **MUST** show **`OpsEmptyState`** (or equivalent) with copy that **explains** **why** (e.g. “No bookings match these filters for the selected window”) — **US-E2** AC.

9. **Detail alternative:** Where a KPI is **inherently** a **single-entity** metric (if any in v1), drill **may** land on an **existing** booking/trip detail route **if** the team documents the **ID resolution** rule; otherwise **prefer** **`/ops/search`** or **`/ops/trips`** list filters — **US-E2** AC.

### Cross-cutting

10. **Data access:** Prefer **server components** + **`createUserServerClient`** for **aggregate** reads (counts, grouped summaries); **document** any **client** refetch or **realtime** use in [`docs/ops-data-freshness.md`](../ops-data-freshness.md). If KPIs **subscribe** to **realtime**, reuse **`src/features/ops/components/OpsBoardRealtimeBridge.tsx`** (or successor) **only** with **subscription error** handling consistent with **11.2** — **AC4–AC5** reinforcement.

11. **Logging:** On **server** failures loading dashboard aggregates, emit **`logOpsAction`** (or project equivalent from **11.2**) with **action name**, **outcome**, **safe correlation ids**, **PII minimization** — [`docs/ops-server-action-logging.md`](../ops-server-action-logging.md).

12. **Navigation shell:** If the dashboard introduces a **new** primary ops entry, update **`src/features/ops/ops-nav-config.ts`** (and **`/ops` redirect** in **`src/app/(ops)/ops/page.tsx`**) **as agreed** in **Tasks** so staff can **discover** the surface without dead links.
