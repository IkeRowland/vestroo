# Story 1.3: Pricing & Payment

## Status: Done

## Story

- As a **traveler**
- I want to **see the final price clearly displayed and complete secure payment processing through PayFast**
- so that **I can confidently pay for my booking and receive confirmation**

## Acceptance Criteria (ACs)

1. **AC1:** The system MUST clearly display the final price breakdown (base price, any applicable fees, total amount) before payment submission on the Payment page.

2. **AC2:** The system MUST integrate with PayFast Onsite payment gateway for secure online payment processing without full page redirection.

3. **AC3:** The system MUST generate a secure PayFast payment signature server-side using the merchant passphrase (never exposed to client).

4. **AC4:** The system MUST create a booking record in Supabase with status 'pending' before initiating payment, storing all booking details (route, passenger info, total amount, payment reference).

5. **AC5:** The system MUST handle PayFast payment webhook callbacks to update booking status from 'pending' to 'paid' upon successful payment confirmation.

6. **AC6:** The system MUST handle payment failures gracefully, displaying appropriate error messages and allowing the user to retry payment.

7. **AC7:** The system MUST redirect users to the confirmation page (`/confirmation`) with booking ID upon successful payment completion.

8. **AC8:** The system MUST validate all payment-related data (amount, booking ID, customer details) before processing payment requests.

9. **AC9:** The Payment page MUST be accessible only when the user has completed previous steps (quote selected, customer details provided) - redirect to appropriate step if prerequisites not met.

10. **AC10:** The system MUST display payment security indicators (SSL/TLS, PayFast branding) to build user trust.

## Dev Technical Guidance

### Story Context & Dependencies

This story implements the **PayFast payment integration** for the booking flow. It builds directly on:
- **Story 1.1**: Booking search and quote calculation (provides quote data in Zustand store)
- **Story 1.2**: Multi-step checkout process (Payment page created as placeholder, now needs full implementation)

The Payment page (`/book/payment`) was created in Story 1.2 with a placeholder "Pay Securely" button. This story makes that button functional by integrating PayFast Onsite payment processing.

### Key Technical Requirements

#### PayFast Integration Pattern

Based on the architecture documentation (`docs/architecture.md#PayFast-Onsite`), the integration follows this flow:

1. **Server-Side (processPayment.ts)**:
   - Create booking record in Supabase with status 'pending'
   - Generate PayFast payment signature using merchant credentials
   - Return payment parameters (amount, merchant ID, signature, etc.) to client

2. **Client-Side (Payment Page)**:
   - Receive payment data from Server Action
   - Initialize PayFast Onsite modal with payment parameters
   - Handle payment callbacks (success/failure)

3. **Webhook Handler (API Route)**:
   - Receive payment confirmation from PayFast
   - Verify webhook signature
   - Update booking status from 'pending' to 'paid' in Supabase

#### PayFast Onsite Implementation

Reference: `docs/api-reference.md#PayFast-Onsite`

- **Authentication**: Merchant ID + Signature (server-side generation)
- **Flow**: Application generates signature → Frontend triggers PayFast Modal → Webhook confirms payment
- **Security**: Passphrase MUST NEVER be exposed to client (server-side only)

#### Data Model Requirements

Reference: `docs/data-models.md#Booking`

The Booking entity must include:
- `status: 'pending' | 'paid' | 'confirmed' | 'completed' | 'cancelled'`
- `total_amount: number` (final price)
- `payment_reference: string` (PayFast transaction reference)

Additional fields needed for payment tracking:
- `payment_status: 'pending' | 'paid' | 'failed' | 'refunded'`
- `transaction_id: string` (PayFast transaction ID)
- `payment_timestamp: Date`

#### Server Action Implementation

Reference: `docs/frontend-architecture.md#API-Interaction-Layer`

The `processPayment` Server Action should:
- **Input**: Full booking state from Zustand store (from Stories 1.1 and 1.2)
- **Logic**: 
  1. Validate booking data using Zod schema
  2. Create booking record in Supabase (status: 'pending')
  3. Generate PayFast signature with merchant credentials
  4. Return payment data object
- **Output**: `Promise<{ bookingId: string, payFastData: PayFastPaymentParams }>`

#### Webhook Handler Implementation

Create `src/app/api/payfast/webhook/route.ts`:
- Handle POST requests from PayFast
- Verify webhook signature for security
- Parse payment status from payload
- Update booking in Supabase
- Return appropriate HTTP status (200 for success, 400/500 for errors)

**Important**: Implement idempotency to prevent duplicate status updates if PayFast retries the webhook.

#### Environment Variables

Reference: `docs/environment-vars.md`

Required environment variables:
- `PAYFAST_MERCHANT_ID` (NEXT_PUBLIC_* for client-side)
- `PAYFAST_PASSPHRASE` (server-side only, never exposed)
- `PAYFAST_MERCHANT_KEY` (if required by PayFast API version)
- `PAYFAST_URL` (sandbox: `https://sandbox.payfast.co.za`, production: `https://www.payfast.co.za`)

#### Payment Page Updates

Reference: `docs/frontend-architecture.md#Routing-Strategy`

The Payment page (`src/app/(app)/book/payment/page.tsx`) should:
- Display final price breakdown clearly (see UI/UX specs below)

- Validate prerequisites (redirect if quote or customer details missing)
