## Story

- As an **account admin**, I need **`/account/members`** to **list** members and **pending invites**, **invite** colleagues, **change roles**, and **remove** membership, with a **last-admin** guard and **auditable** changes, so that **I can onboard and offboard team members** without ops (per **US-A3**), while **bookings** created by removed users **remain** on the account.

## Acceptance Criteria (ACs)

1. **Replaces 15A.2 stub:** **`src/app/(account)/account/(portal)/members/page.tsx`** is no longer only the “ships in 15A.5” placeholder. It implements the **admin-only** **members** experience for the **active** `customer_accounts` context (same invariants as other portal routes: **server-side** active account, **no** client-trusted account id for authZ).

2. **Auth — double gate:** The route uses **`requireAccountMemberPage`** (or a helper that **wraps** it) **and** enforces **role === `admin`** for the **active** membership. **Booker** and **rider** must not access the page: respond with **403** **or** the project’s standard **forbidden** behaviour (**survey:** today **`requireAccountPortalRoles`** may **redirect** to `/account` — align **non-admin** with product; document final choice in **Progress Notes**).

3. **List:** Server-loaded **table or list** of **`customer_account_members`** rows for **`account_id = activeAccountId`**, including **pending invites** — rows where **`accepted_at IS NULL`**. Show **email** (table key), **role**, **invite / accept** status (e.g. pending vs accepted via **`accepted_at`** / **`invited_at`**) **and** **`profile_id`** when present. Use **"—"** for optional display fields (e.g. unlinked name) **if** not stored; do **not** invent data.

4. **Invite (pending row):** **“Invite member”** creates a **`customer_account_members`** row for the **active** account with: **`email`**, role as chosen, **`accepted_at IS NULL`**, and **`invited_at`** set (default or explicit). **`profile_id`** is **null** until the invitee signs up and is matched (per **VST-14** comment: backfill on first login) — **survey** exact insert shape and any trigger expectations.

5. **Email / URL — split from 15A.6:** **Server path** (invite action) **persists** the pending member and **appends `ops_audit_log`** (see AC9). **Sending** the invite email, **template** registration, and **signup landing** are **15A.6** **unless** the repo already exposes a **reusable** “send account invite” path — then optionally wire **minimal** send and document reuse in **Progress Notes**. **Default AC:** UI includes traceable copy such as **“Full invite email ships in 15A.6”** and/or a **copy-paste invite URL** stub (e.g. tokenised or placeholder URL pattern **documented** as temporary).

6. **Role change:** Admin can change a member’s **role** among **`admin` / `booker` / `rider`** (same validation as DB `CHECK`). **Pending** invite rows: **survey** product rule — e.g. allow role update before accept, or restrict to accepted rows only; document in **AC** or **Progress Notes**.

7. **Remove membership:** **Remove** (or “Revoke access”) **deletes** the **`customer_account_members`** row for that **`(account_id, email)`** **or** applies a **soft-delete** pattern if introduced — **survey** DB and product; **document the actual behaviour** in **Progress Notes**. **Bookings** (and other records) **created by** that user **while** they were a member **remain** associated with the **account** (no orphaning of booking history for the org).

8. **Last-admin guard:** **UI** and **server** (invite/update/remove) **refuse** any operation that would leave the account with **zero** **`admin`** members (e.g. demote/remove/downgrade the last admin). Error messaging must **not** leak other accounts’ data.

9. **Audit — every member change:** **`ops_audit_log`** records **each** of: **invite created**, **role changed**, **member removed** (and **any** other write covered by this story) with a non-null **`actor_id`** = the **acting admin**’s user id, **and** a structured **`payload`** (e.g. target email, old/new role, action type). Reuse or extend **`src/lib/ops-audit.ts`** `appendOpsAuditLog` (or equivalent) — **survey** `actor_role` / entity naming for **customer**-portal actions so inserts satisfy RLS and FK constraints.

10. **Optional — Invite throttle (Epic §6):** If feasible within scope, **server** invite-creation enforces a **rate limit** (e.g. **max 10 successful invite attempts per admin per rolling hour**). If not implemented, document as **deferred** in **Progress Notes** with a pointer to the risk line.

11. **RLS / migrations:** If **authenticated** user JWT cannot **INSERT/UPDATE/DELETE** `customer_account_members` per current policies, ship a **minimal** migration: **admin-on-active-account** policies **or** a documented **service-role** server path (prefer **RLS**-aligned, auditable). **No** cross-account write paths.

12. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **US-A3**; catalogue **15A.5**; **15A.6** / **15A.3**–**15A.4** / **15A.7**–**15A.10** explicitly excluded where listed above.

- **Last-admin guard:** Count **accepted** admins only (`role = admin` AND `accepted_at IS NOT NULL`). Enforced in `src/actions/accountMembers.ts` for demote and remove. **Invite** cannot bypass (inviter is always an accepted admin).
- **Pending role edits:** **Allowed** before accept (product choice).
- **Audit:** `appendOpsAuditLog` with `actor_role = 'account_portal'` (new enum value + policy `ops_audit_log_account_portal_insert`). **`entity`** = `customer_account_members`; **`entity_id`** = active `customer_accounts.id`; **`action`** ∈ `account_member_invited` | `account_member_role_changed` | `account_member_removed`. **`payload`** includes `account_id`, `target_email`, role fields (Epic 15 exception to “no PII in payload” for this traceability). **`actor_id`** = acting user. On audit failure after mutation, **rollback** invite / role / remove (remove restores row snapshot).
- **Non-admin access:** **`requireAccountPortalRoles(admin)`** — **redirect to `/account`** (same as previous stub); not 403.

- **Self-remove cookie:** If the removed row’s `profile_id` is the acting user, cookie is set to another accepted membership or cleared.
