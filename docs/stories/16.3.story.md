## Story

- As an **architect** (and **any migration author**), I need a **published ADR** that defines when **`SECURITY DEFINER STABLE`** helpers are mandatory for cross-table RLS and triggers, **why** inline **`EXISTS`** fails (`42P17`), **how** to name and **grant** helpers, and **what smoke coverage** new policies require, with a **worked example** from the shipped **K1** migration, so **Theme O** is the single convention doc, **Epic 6 BE.6.2** and **CONTRIBUTING** point authors to it, and **US-O2** can reference a stable **`docs/adr/0006-rls-cross-table-helpers.md`** path.

## Acceptance Criteria (ACs)

1. **New ADR** at **`docs/adr/0006-rls-cross-table-helpers.md`** containing at least:
   - **Rule:** Any RLS policy **`USING`** or **`WITH CHECK`** that references rows in **another** table must do so via a **`SECURITY DEFINER STABLE`** SQL helper, **not** via inline **`EXISTS`** into that other table under the invoker’s RLS. The same rule applies to **trigger functions** that touch **multiple** RLS-protected tables when the alternative would inline cross-table predicates subject to mutual RLS evaluation.
   - **Rationale:** Inline **`EXISTS`** evaluates the other table’s RLS; if that table’s policy references back, PostgreSQL can raise **SQLSTATE `42P17`** (infinite recursion detected in policy).
   - **Pattern reference:** **`booking_is_visible_to_chauffeur_via_trips`** — **[`docs/epic-11.md`](../epic-11.md)** **E1** as canonical prior art; **K1** helpers **`service_run_is_visible_to_party`**, **`ticket_is_visible_to_run_chauffeur`** as further **shipped** examples (with migration filename **`20260426170000_ops16_service_runs_tickets_rls_helpers.sql`**).
   - **Naming convention:** **`<source_table_singular>_is_visible_to_<role_or_relationship>(p_<source_table_singular>_id uuid) returns boolean`** (align parameter name with table naming; document examples matching K1 + E1).
   - **Grants:** For helpers invoked from RLS: **`REVOKE ALL ON FUNCTION … FROM PUBLIC;`**, **`GRANT EXECUTE … TO authenticated;`**, **`GRANT EXECUTE … TO service_role;`** (document the pattern; cite K1 migration as example).
   - **Smoke test requirement:** Every **new** policy MUST be accompanied by an assertion in **`supabase/smoke_rls.sql`** that **`select count(*) from <table>;`** (or equivalent safe read agreed with QA) runs cleanly under the **relevant role(s)** — state expectation without implementing the US-M2 catalogue or US-O2 global loop.
   - **Exceptions:** Same-table self-referencing policies (e.g. customer-sees-own-row) **do not** require the helper pattern — document clearly to avoid false expectations before **US-O2** lint lands.

2. **Cross-links** — ADR discoverable from:
