## Story

- As **ops staff**, I need an **"Identify client"** action on each **`/ops/bookings`** row (**12.3**), so that **misclassified** **`client_type`** / account linkage can be corrected **before payment settles**, within **Q5** bounds.
- As **ops staff**, when I link, create an account inline, or revert to walk-in, the **list** and **badges** reflect the change without stale UI — using **12.4** realtime if active or **`router.refresh()`** (or equivalent) after successful mutation (**E2**).

## Acceptance Criteria (ACs)

### US-D2 — Identify client on booking row (Theme D, **Q5**)

1. **Unpaid — picker (Q5 retro-link bounds):** When the booking's **`payment_status`** is **not** **`'paid'`**, the action opens a flow (dialog/sheet — name TBD) that allows: **link** to an **existing** **`customer_accounts`** row, **create a new account inline** (staff-only; uses existing **`customer_accounts_staff_insert`** / staff session — no new catalogue exposure beyond staff RLS), or **revert** **`account_client` → `walk_in`** (clear account linkage per AC4).

2. **Paid — disabled + tooltip:** When **`payment_status = 'paid'`**, the action is **disabled** with tooltip: *"Paid walk-ins can't be retro-linked. Reason: finance reconciliation."* — the **same** constraint applies to **unlinking** a paid **`account_client`** (no UI path that attempts illegal unlink / relink).

3. **Successful link:** **`client_type` → `'account_client'`**, **`customer_account_id`** set to the chosen account, **`account_snapshot`** populated from the **current** **`customer_accounts`** row at link time (fields per **12.1** / migration — use types, do not invent snapshot keys).

4. **Successful unlink (revert to walk-in):** **`client_type` → `'walk_in'`**, **`customer_account_id`** cleared, **`account_snapshot`** cleared (null / empty per DB JSON semantics in types).

5. **`ops_audit_log`:** On every successful **link** or **unlink**, insert a row with **`action='identify_client'`** and **`payload`** containing at least: **`prior_client_type`**, optional **`new_customer_account_id`** (after state), optional **`prior_customer_account_id`** (before state) — matching epic **§4 Theme D** line **150** (extend with **`booking_id`** in payload only if needed for queries; document any additive keys).

6. **Constraint safety:** **`bookings_account_linkage_check`** is **never** violated — the UI and server action **reject** or **disable** combinations that would fail the constraint; server remains authoritative (no reliance on UI-only checks).
