## Story

- As **ops staff**, I need **Check availability** screens on **walk-in** and **account** workflows that show **vehicle** and **driver** occupancy across the **pickup ±2h** window, highlight **conflicts**, let me **pick one vehicle and one driver**, and **save** an audit snapshot, so I **don’t commit** quotes or assignments blind.

- As **ops staff**, I need **loading**, **error**, and **success feedback** consistent with other ops surfaces (**`OpsLoadingRegion`**, **`OpsErrorState`**, toasts).

- As **ops staff on mobile**, I need the strips to **reflow** so the check remains usable on a narrow viewport.

## Acceptance Criteria (ACs)

1. **Routes:** **`/ops/walk-in/[bookingId]/availability`** and **`/ops/accounts/[bookingId]/availability`** exist; each loads booking context appropriate to **`client_type`** (**walk-in** vs **account**); invalid/mismatched type yields **not found** or **forbidden** per repo ops patterns.
2. **Strips — vehicles:** Default window = **pickup ±2h**. **Y:** candidate **vehicles** with **capacity ≥ booking passengers**; **X:** time; **`trips`** and **`chauffeur_assignments`** overlapping the window render as **blocks**; **conflicts** use **red** styling (same semantics as highlight driving rationale rule).
3. **Strips — drivers:** Second strip: **driver** rows (staff profiles with chauffeur role / active roster — **Task 0** survey), assignments as blocks; **red** conflict highlighting for the same window.
4. **Selection:** Click (or accessible equivalent) chooses **exactly one** vehicle and **one** driver; selection is **sticky** for the **client session** (tab state — see provenance).
5. **Rationale:** **Textarea**, **max 500** characters; **required** if **any** visible conflict exists among **considered** candidates; **optional** otherwise; **disabled submit** + **field error** when required but empty; **server** rejects with validation error if rule violated or **length > 500**.
6. **Submit:** **`submitAvailabilityCheckAction`** (name reconciled in **Task 0**) accepts input shaped per epic: **`{ bookingId, selectedVehicleId, selectedDriverId, rationale, candidatesConsidered: { vehicleIds: string[], driverIds: string[] } }`**. On success: sets **`availability_checked_at = now()`**, **`availability_checked_by = auth.uid()`**, **`availability_check`** jsonb snapshot; **`revalidatePath`** / cache rules per ops actions; **redirect** to **`/ops/bookings/[id]`** with **`id = bookingId`**.
7. **UX polish:** **Loading** uses **`OpsLoadingRegion`**; **errors** use **`OpsErrorState`** (or **`OpsFetchErrorIsland`** where consistent with queues); **success** uses the same **toast** pattern as other **Theme B** ops server actions (**Task 0** survey **`markBookingPaymentReceived`** / **`sendWalkInQuote`**).
8. **Mobile:** On narrow viewports, strips **stack vertically** (or equivalent vertical time axis) without horizontal-only reliance.
9. **Quality:** **`npm run lint`** and **`npm run test`** remain green; **Vitest** covers the server action (validation, auth, snapshot shape, conflict+rationale); **optional** RTL test for **`AvailabilityCheckPanel`** if high value.

## Story Progress Notes

### Agent Model Used: Claude Opus 4.7 (Cursor `dev` subagent)

### Completion Notes List

- **(a) Action filename + export reconciliation:** Single module **`src/actions/opsAvailabilityCheck.ts`** exporting **`submitAvailabilityCheckAction`** — reconciles **epic §8** path with **US-B2** export name; matches existing **`camelCase`** ops action style (e.g. `markBookingPaymentReceivedAction`, `sendWalkInQuoteAction`). The action's Zod input schema includes a `scope: 'walk_in' | 'account_client'` field (validated server-side against **`bookings.client_type`**) so a single entry-point serves both routes without per-route wrappers.
- **(b) Timezone:** Internal window math is **UTC** end-to-end (booking `pickup_datetime` is `timestamptz`, stored UTC). The shared helper **`src/lib/ops-availability-window.ts`** computes `pickup − 2h` to `pickup + max(estimated_duration, 0) + 2h` in UTC milliseconds + ISO strings. Display formatting in `AvailabilityCheckPanel` uses `Intl.DateTimeFormat('en-ZA', { timeZone: 'Africa/Johannesburg' })` for tick labels and the booking summary header. Symmetric ±2h math means there is no DST hazard.
- **(c) Driver query source:** **`profiles`** (filtered by `role = 'chauffeur'` and `status = 'active'`), aligning with `assignBookingToRun` driver-resolution. The **`driver_assignments`** view is *not* used as the candidate source; conflicts are detected directly against the base **`chauffeur_assignments`** table (consistent with `findChauffeurWindowConflicts` semantics).
- **(d) `sessionStorage` decision:** **Not used.** Selection (`selectedVehicleId`, `selectedDriverId`, `rationale`) lives in component-level **`useState`** at `AvailabilityCheckPanel` scope. Tab-level stickiness was the user-requested target; refresh resets state, which is acceptable per the story's "client tab state" wording. Adding `sessionStorage` would add cleanup-on-submit complexity for marginal UX value.
- **(e) Mobile breakpoint:** **`md:` (768px)**, matching **16.20** (`WalkInQueueView`) so the strips reflow consistently with the queue tabs. Above `md`, each candidate row renders an absolute-positioned horizontal timeline with overlapping commitment blocks. Below `md`, the same row renders a vertical chip stack (`Timestart–Timeend`) so red conflict styling and free/conflict badges remain visible without horizontal scrolling.
- **(f) JSONB key casing:** **`snake_case`** throughout the `availability_check` payload and the audit `payload`: `selected_vehicle_id`, `selected_driver_id`, `candidates_considered.{vehicle_ids,driver_ids}`, `rationale` (nullable), `has_conflict` (server-recomputed), `window.{start,end}` (ISO UTC). Matches `markBookingPaymentReceived` audit payload and `assignBookingToRun` precedent. Audit log `action` column = `submit_availability_check` (imperative verb style consistent with `payment_received_eft`, `assign_booking_to_run`).
- **Audit + revalidation:** Action writes one **`ops_audit_log`** row via `appendOpsAuditLog` with `actor_role` ∈ `{dispatcher, admin}` and the same snapshot plus `client_type`. Revalidates `/ops/bookings`, `/ops/bookings/${bookingId}`, and the matching `/ops/walk-in` or `/ops/accounts` queue, then `redirect('/ops/bookings/${bookingId}')` — segment is `id`, not `bookingId`, per the canonical detail route.
- **Conflict semantics (server recompute):** Vehicles/drivers in **terminal status** (`cancelled`, `completed`) are *not* counted as conflicts on either client highlight or server rationale gate, so a cancelled trip overlap does not force a rationale.
- **Defense-in-depth on submit:** Server verifies (i) selected vehicle exists in `vehicles`, (ii) selected driver is an *active* `chauffeur` profile, (iii) the booking row's `client_type` matches the route scope (`SELECTED_VEHICLE_NOT_CONSIDERED`, `SELECTED_DRIVER_NOT_CONSIDERED`, `INVALID_CLIENT_TYPE`, `INVALID_VEHICLE`, `INVALID_DRIVER`).
- **N+1 avoidance:** The page-level loader (`loadAvailabilityCheckContext` in `src/lib/ops-availability-loader.ts`) issues at most **5** queries regardless of candidate count: `bookings`, `vehicles` (with `vehicle_categories` join for capacity), `profiles`, `trips` filtered by candidate-vehicle-ids ⊕ candidate-driver-ids (two `IN` queries with bounded list), and one `chauffeur_assignments` query.
- **UX feedback parity with Theme B:** Existing ops actions (`sendWalkInQuoteAction`, `markBookingPaymentReceivedAction`) surface failures via inline `<p role="alert">` rather than a global toast library. Replicated that pattern: server failures render inline near the submit button with the correlation-id stub; success path relies on the action's own `redirect` to navigate to the booking detail (no toast dependency added).
- **Tests:** `src/actions/__tests__/opsAvailabilityCheck.test.ts` — 17 unit tests covering: malformed payload, rationale > 500, non-staff caller, selected-not-considered (vehicle + driver), missing booking, scope mismatch, missing pickup window, vehicle conflict requires rationale, driver assignment conflict requires rationale, terminal-status conflicts excluded from rule, snake_case snapshot shape + audit + revalidate + redirect, rationale persisted when conflict + provided (account-client variant), `INVALID_VEHICLE`, `INVALID_DRIVER`, `DATABASE` on update fail, `AUDIT` when audit append fails. `npm run lint` clean (warnings only, all pre-existing); `npm run test -- --run` 605 / 605 across 101 files.
- **Out of scope (verified untouched):** US-B3 guardrail rejection codes on `sendWalkInQuote` / `assignBookingToRun`; US-B4 admin override; Theme A nav changes (16.22). No new migrations — existing `availability_checked_*` columns from B1 (16.9) cover persistence.
