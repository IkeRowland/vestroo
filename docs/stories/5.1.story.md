# Story 5.1: Ops console information architecture & navigation shell

## Status: Done

**Dependencies:** **[VST-7](vst-7.story.md)** (and **`docs/ops-console.md`**) establish the **`/ops/*`** surface, **`requireOpsStaffPage`**, staff roles (**`dispatcher`**, **`admin`**), and public **`/ops/login`** / **`/ops/unauthorized`**. This story **refactors chrome only**; it MUST **not** remove or bypass server gates (**NFR.5.3**). **FE.5.2** (Tailwind design system ADR/tokens) is a **separate** epic story; here, prefer **existing** Tailwind + **`src/components/ui/*`** / Radix patterns and keep styling **consistent** with current ops dark chrome unless a follow-on story explicitly extends tokens.

## Story

- As an **operations staff member** (dispatcher or admin)
- I want a **dashboard shell** with **persistent sidebar**, **top bar**, and **clear location** (breadcrumbs or title hierarchy), with **navigation grouped by domain** and **role-appropriate items**
- so that I can **find tools quickly**, **deep-link and use browser history safely**, and **trust that what I see matches what I am allowed to do** (server remains authoritative)

## Epic traceability (source)

**From `docs/epic-5.md` — FE.5.1:** Replace the **primary** ops navigation model from a **single header row of equal-weight links** with a **dashboard shell**: collapsible **sidebar** (or equivalent persistent nav) grouping areas **by domain** (e.g. fulfilment, fleet, people, finance/compliance, configuration), plus a **top bar** for **global actions** (search, notifications placeholder, profile/sign-out). The shell MUST expose **current location** via **breadcrumbs** or a **clearly labeled page title hierarchy**. **Deep links** and **browser back/forward** MUST remain valid. Implementation MUST be scoped to **`(ops)`** so **marketing** and **public booking** layouts are unchanged. Where Vestroo distinguishes **multiple staff roles**, navigation MUST support **role-aware visibility** (reference **interaction** pattern: capstone **`frontend-manager`** **`Menu.tsx`** with per-item **`visible: ["admin" | "manager"]`**) while **server-side authorization** remains authoritative — see **NFR.5.5**.

**Constraining NFRs (Epic 5):**

- **NFR.5.3 (Security):** Shell changes MUST **not** weaken **`requireOpsStaffPage`** / **`requireChauffeurPage`** gates; role checks remain **server-first**.
- **NFR.5.4 (Consistency):** **Epic 4 / VST** domain language takes precedence over capstone **demo naming** in **user-visible** strings and **new** routes.
- **NFR.5.5 (Authorization alignment):** **Role-based nav** MUST match **server-enforced** permissions: users MUST NOT see links to actions they cannot perform; **hidden** routes MUST still **403/redirect** if hit directly (e.g. direct URL to an admin-only capability must **not** succeed for a dispatcher).

**Reference-only (interaction, not auth/transport):** `docs/capstone-reference/frontend-manager/src/components/Menu.tsx` — illustrates **filtering menu items by role** (`visible` arrays). Vestroo uses **`ProfileRole`** from **`profiles.role`** and **`src/lib/ops-auth.ts`**; do **not** copy capstone **`localStorage` JWT** or client-only auth assumptions.

## Acceptance Criteria (ACs)

1. **Dashboard shell structure:** **`src/app/(ops)/ops/layout.tsx`** (or a **small** set of colocated layout components under **`src/features/ops/`**) implements a **persistent sidebar** plus a **main column** with a **top bar**. The **old pattern** of a **single horizontal row of equal-weight nav links** as the **primary** ops navigation MUST be **replaced** (secondary compact actions in the top bar are allowed).

2. **Collapsible sidebar:** The sidebar MUST be **collapsible** (e.g. icon-rail vs expanded labels) at **desktop** widths, with a **clear control** (button) that is **keyboard** operable and has an **accessible name** (e.g. `aria-label`). **Tablet** behaviour SHOULD avoid horizontal clipping of **primary** nav (align with **FE.5.7** intent — minimal acceptable: scrollable sidebar or collapse default at narrow widths).

3. **Domain-grouped navigation:** Sidebar items MUST be **grouped** under **domain-oriented** sections (labels may be refined with product, but MUST map sensibly to existing routes), for example:
   - **Fulfilment / trips:** e.g. Board, Calendar, Fulfil, Trips, Search (staff booking entry) — use **Vestroo-preferred labels** per **NFR.5.4** (e.g. avoid capstone **“trip”** wording clashes where VST uses **booking / trip / run** consistently elsewhere).
   - **Fleet:** Vehicles (and future fleet sub-routes if present).
   - **People / field alignment:** Roster (chauffeurs).
   - **Finance & compliance:** Invoicing, Compliance.
   - **Product / engagements:** Experiences (grouping must not orphan current **`/ops/*`** pages from **`docs/ops-console.md`**).

4. **Top bar — global affordances:** The top bar MUST include: **staff search placeholder** (UI stub acceptable: disabled input or button that navigates to **`/ops/search`** / focus target — no requirement for global search backend in this story), **notifications placeholder** (non-functional badge or “Coming soon” is acceptable), and **profile / sign-out** (existing **`OpsSignOutButton`** MUST remain available; optional display of **role** or **email** if low-effort from session).

5. **Location awareness:** Every ops child route MUST show **either** (a) **breadcrumbs** reflecting **`/ops/...`** segments with human-readable labels, **or** (b) a **consistent page header** pattern (title + optional subtitle) wired from a **single** shared primitive so **hierarchy** is obvious. **Deep links** to existing routes MUST still render with correct **location** cues.

6. **Routing integrity:** **No breaking change** to existing **`/ops/*`** URLs documented in **`docs/ops-console.md`**. **Browser back/forward** and **direct URL** entry MUST continue to work. **`await requireOpsStaffPage()`** MUST remain the **first** authoritative gate in the authenticated ops layout (or equivalent **strictly before** rendering protected chrome).

7. **Scope isolation:** Changes MUST be confined to the **`(ops)`** route group and **`src/features/ops/**`** (and shared UI under **`src/components/ui/*`** if reused). **`(marketing)`**, **`(app)`** booking, and **`(field)`** layouts MUST be **unchanged**.

8. **NFR.5.3 — Gates preserved:** **`requireOpsStaffPage`** behaviour (redirect to **`/ops/login`** / **`/ops/unauthorized`**) MUST remain **functionally equivalent** for all **`/ops/*`** pages under this layout. **`middleware.ts`** continues to set **`x-pathname`** for **`/ops`** and **`/field`**; do **not** remove or weaken that contract if any child still relies on it.

9. **NFR.5.5 — Nav matches server rules:** Nav visibility MUST reflect **dispatcher** vs **admin** where the **server** already distinguishes (e.g. **DSR / anonymise** and other **`getOpsAdminForAction()`**-gated capabilities): **dispatchers** MUST NOT see **admin-only** destinations in the shell. For any route that is **staff-visible** but contains **admin-only sub-actions** (e.g. compliance page), the **route** may remain visible to dispatchers while **actions** stay server-gated — document the chosen rule in **Dev Technical Guidance** so behaviour is **consistent** and **predictable**.

10. **NFR.5.4 — Vocabulary:** New **user-visible** labels for groups or breadcrumbs MUST follow **Vestroo / VST** terminology (**`docs/epic-4.md`**, existing ops pages, **`docs/ops-console.md`**) — not capstone demo Vietnamese/English labels from reference files.

11. **Accessibility baseline (shell-level):** Landmarks: **`header`**, **`nav`** (sidebar), **`main`**. **Skip link** to **`main`** SHOULD be added if straightforward. **Visible focus** on sidebar toggle and nav links; **icon-only** controls MUST have **`aria-label`**. (Full **FE.5.8** polish may extend this story’s baseline in a later story.)

12. **Documentation:** Update **`docs/ops-console.md`** to describe the **new shell** (sidebar groups, top bar, breadcrumbs/title pattern) and note **role-based nav** alignment with **`ops-auth`**. Optionally add a one-line pointer in **`docs/front-end-routing-strategy.md`** that **`/ops/*`** detail lives in **`docs/ops-console.md`** (that doc is currently booking-heavy).

## Dev Technical Guidance

### Current implementation (replace primary nav pattern)

- **Layout gate:** `src/app/(ops)/ops/layout.tsx` calls **`requireOpsStaffPage()`** then renders a **single `<header>`** with **many `<Nav>` links** in one row — this is the **FE.5.1** anti-pattern to replace with **sidebar-primary** IA.
- **Auth helpers:** `src/lib/ops-auth.ts` — **`STAFF_ROLES`**: `dispatcher`, **`admin`**; **`requireOpsStaffPage()`** for layouts; **`getOpsStaffForAction()`** / **`getOpsAdminForAction()`** for Server Actions.
- **Roles type:** `src/types/database.types.ts` — **`ProfileRole`** includes **`customer` | `chauffeur` | `dispatcher` | `admin`**; ops staff are **`dispatcher`** and **`admin`** only.
- **Middleware:** `middleware.ts` sets **`x-pathname`** for **`/ops`** and **`/field`** — preserve unless a tracked follow-up removes all consumers.
- **Public ops routes:** `src/app/(public-ops)/ops/login/page.tsx`, **`.../unauthorized`** — **outside** **`(ops)`** group; MUST remain **unchanged** in behaviour.

### Route inventory (must remain reachable)

From **`docs/ops-console.md`**: **`/ops`** → board redirect; **`/ops/board`**, **`/ops/calendar`**, **`/ops/fulfil`**, **`/ops/trips`**, **`/ops/vehicles`**, **`/ops/roster`**, **`/ops/compliance`**, **`/ops/invoicing`**, **`/ops/experiences`**, **`/ops/search`**.

### Admin vs dispatcher

- **`src/app/(ops)/ops/compliance/page.tsx`** — uses **`staff?.role === 'admin'`** for **DSR** panel copy; **nav rule** should match product: either **hide** entire **Compliance** for non-admin **or** keep page for both but **hide admin-only** **nav** entries only if separate routes exist. **Epic** allows page-level staff access with **action-level** admin gate — **state the chosen UX** in PR / Progress Notes and apply **NFR.5.5** consistently.

### Reference pattern (interaction only)

- **`docs/capstone-reference/frontend-manager/src/components/Menu.tsx`** — `menuItems[].visible` role filtering. Mirror the **idea** with **`ProfileRole`** and server-aligned rules — **not** the capstone **`role`** import or JWT session model.

### Docs to read

- **`docs/ops-console.md`** — authoritative **`/ops`** route table and auth notes.
- **`docs/epic-5.md`** — FE.5.1 + NFR.5.3–5.5.
- **`docs/epic-4.md`** — domain vocabulary / VST alignment (**NFR.5.4**).
- **`docs/frontend-architecture.md`**, **`docs/repo-conventions.md`** — where to place **`src/features/ops`** components.
- **`docs/field-tools.md`** — **`/field/*`** is **out of scope** for this story (**NFR.5.3** mentions **`requireChauffeurPage`** — do not regress field).

### Suggested technical approach

- Prefer **Server Component** layout passing **`session.role`** into **client** sidebar only if **interactivity** (collapse state) requires **`useState`**; otherwise keep **max** in RSC.
- Consider **Radix** **Collapsible** or **Dialog** for mobile nav if needed; **do not** introduce **Ant Design** (**FE.5.2**).
