## Story

- As an **account member** (per **Q24**), I need a **portal preference centre at `/account/preferences`**, **scoped to my** **`customer_account_members`** row in the **active** account, so that **I can** turn **informational** and **marketing** **email** categories on or off, **see that transactional email cannot be disabled**, **save immediately**, and have **changes audited** — **without** another member or account **changing my** preferences, and with **defaults** that respect **POPIA** (marketing off until I opt in).

## Acceptance Criteria (ACs)

1. **Route & shell:** A Next.js page exists at **`/account/preferences` under `src/app/(account)/account/preferences/`** (or equivalent under the same **`(account)/account/`** group as **[`15.1.story.md`](15.1.story.md)**). It uses the **portal layout** and **auth + membership gating** from **`15A.1`**; unauthenticated or ineligible users do not reach a state where they can **mutate** another member’s preferences.

2. **UI — categories (email):** The page shows **three** comms **categories** for the purpose of this story: **`informational`**, **`marketing`**, and **`transactional`**. **Toggles (or equivalent controls) allow changing `informational` and `marketing` only.** **`transactional` is always “on”** in the UI (**disabled/locked** control + short copy that operational/required email cannot be turned off).

3. **Defaults (POPIA + epic):** On first load / when **`comms_preferences` is null or incomplete**, **apply defaults in application or migration defaults** as: **informational = on**; **transactional = on** (must remain on); **marketing = off** (explicit opt-in for marketing). Persisted representation must match the **documented jsonb shape** once the user **saves** or on **first write**, per team convention (see **AC5**).

4. **`comms_preferences` jsonb — schema & types:** A **`comms_preferences` column** exists on **`public.customer_account_members`** (via **new migration** if not already present — **deferred in [`15.19.story.md`](15.19.story.md)**). The **key names and boolean (or agreed) values** for **`informational`**, **`marketing`**, and **`transactional`** are **documented in this story’s Dev Technical Guidance** and implemented as **shared** types/consts (e.g. under **`src/types/`** — e.g. `CommsPreferenceCategories`, `CommsPreferences` or adjacent to comms types) so **`15C.2` send-time checks** and future **`15C.6` links** share **one** vocabulary. **No ad-hoc string** keys in UI-only code without re-exporting from a single source.

5. **Immediate persist:** When the user **commits** a change (explicit **Save** and/or per-toggle persist — **“immediate” in US-B3**), the **active** membership’s **`comms_preferences`** is **updated** in one **authorised** path (server action or equivalent); **stale** concurrent edits should **not** overwrite another member’s row (row targeted by **RLS** + **membership**, not a client-supplied **member id** for another user).

6. **RLS + server enforcement — no cross-member writes:** **Only** the **authenticated** member’s **`customer_account_members` row** for the **relevant** account (aligned with **active account** from **`15A.1`**) can be **updated** for **preferences**; RLS and/or server checks **block** **cross-member** and **cross-account** updates. **Server-side validation** enforces: **`transactional` cannot** be set to “off” / false; attempts are **rejected** with a clear error.

7. **`ops_audit_log` on every change:** **Every** successful **preference mutation** appends to **`ops_audit_log`** (using existing patterns e.g. **`appendOpsAuditLog`**) with **action** (or product-agreed name) and **payload** including **member** identity reference, **prior** and **new** `comms_preferences` (or a diff), and **active account** context, so compliance review can **reconstruct** history.

8. **Deep-link / query support (forward-compatible for `15C.6`):** The page **reads** an **agreed** query parameter (e.g. **`?category=informational`** or **`?highlight=informational`**) to **scroll to and/or visually emphasise** the **matching** category block. **Document** the **canonical param name(s)** in **Dev Technical Guidance** so **`15C.6`** can embed stable URLs. **If** the category is **unknown/invalid**, fail **gracefully** (no error page — full page still works).

9. **Multi-membership (optional clarity):** If the product treats preferences **per** `customer_account_members` row, changing account via the **`15A.1` switcher** must show the **that membership’s** preferences (or defaults) for the **active** account — no mixing with another account’s stored jsonb. Document behaviour in **Progress Notes** if edge cases exist.

10. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **US-B3** (toggles, transactional locked, `comms_preferences`, `ops_audit_log`, defaults), **Q24** (per-**member** centre), **Theme E `15C.5`**; defers **unsubscribe-in-email** + **POPIA footer in templates** to **`15C.6`**.
