## Story

- As an **account user** (admin, booker, or rider on a customer account), I need a **gated `/account` area** with a **consistent shell** and, when I belong to **more than one** account, an **account switcher**, so that **all portal data can be scoped to the account I am acting in** without cross-org leakage.

## Acceptance Criteria (ACs)

1. **Route group:** New Next.js app-router group **`src/app/(account)/account/`** with its own **`layout.tsx`**. A **`page.tsx`** exists so `/account` resolves (may be a **minimal placeholder** only — see AC9).

2. **Auth — Supabase session:** Unauthenticated users hitting `/account/*` are **redirected to an appropriate login** (reuse or align with existing customer/auth patterns — survey `src/lib/supabase/server.ts`, marketing auth if any). **`middleware.ts`** refreshes the Supabase session for `/account` the same way it does for **`/ops`** and **`/field`** (today only those paths call `refreshSupabaseSessionCookie`).

3. **Auth — membership gate:** After authentication, access is allowed only if the user has at least one **`customer_account_members`** row where **`profile_id`** matches **`auth.users.id`** (same user as `getUser()` in server components) and **`role IN ('admin','booker','rider')`**. Users who are authenticated but **not** eligible are redirected to a **clear forbidden / wrong-surface** experience (dedicated route or shared “unauthorized” pattern — align with **`requireOpsStaffPage`** style in **`src/lib/ops-auth.ts`** but for account members).

4. **Active account resolution:** All server-rendered portal logic for this story uses a single **active `customer_accounts.id`** chosen deterministically:
   - If the user has **one** membership, that account is active.
   - If the user has **multiple** memberships, active account comes from an **explicit selection mechanism** (see AC5), with a **safe default** (e.g. first stable sort by account name or id — document the rule in code comments).

5. **Account switcher (multi-membership only):** When **two or more** eligible memberships exist, the **top nav** (or header region in the account layout shell) shows an **AccountSwitcher** that lists the accounts the user may access and **changes the active account** without logging out. Single-membership users **do not** see the switcher (or see a non-interactive label only — product choice documented in Progress Notes).

6. **Persistence of selection:** Active account survives navigation within `/account/*` via **httpOnly cookie**, **encrypted/signed cookie**, or **query param** — **survey the repo** first; prefer matching any existing org/context pattern. If none exists, **prefer httpOnly cookie** (name e.g. `vestroo_active_account_id` — final name in implementation) set from a **server action** or **Route Handler** when the user switches, with validation that the value is in the user’s **`account_ids_for_current_user()`** set.

7. **RLS alignment — no cross-org reads in app layer:** Portal layout and placeholder page **only** load account-scoped data using the **active account id** combined with the **authenticated user’s** memberships (e.g. filters `WHERE account_id = :active` and membership verified server-side). **Acceptance:** Document in **Progress Notes** how this maps to **`account_ids_for_current_user()`** and existing **`customer_account_members` / `customer_accounts`** RLS (see **`supabase/migrations/*vst14*`**). Any **new** queries introduced in this story must not fetch “all accounts” based on client-supplied ids without server-side membership checks.

8. **RLS verification note:** **Acceptance:** Story **DoD** includes a short **“RLS intent”** bullet: existing Epic **12** RLS is assumed to enforce **no cross-account row access** for members; **full** two-account smoke is **15A.9** — cite **[`docs/epic-15.md`](../epic-15.md)** **15A.9** and **§6** risk “Portal RLS gap”.

9. **Placeholder home (15A.2):** The `/account` **home** content is **not** the full dashboard. At most: account name (or id) for the **active** account, user email, and a **short message** that the dashboard arrives in **Story 15A.2** — no quick-link cards for Bookings / Members / Invoices / New Booking.

10. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **US-A1** items that are **15A.1-only** (layout, gating, switcher, RLS intent); **excludes** US-A1 home quick-links (deferred to **15A.2**).

### Completion Notes List

- **Middleware:** `/account` now mirrors `/ops` and `/field`: `refreshSupabaseSessionCookie`, `x-pathname` header.
- **Routes:** Gated shell under `src/app/(account)/account/(portal)/` (`layout.tsx`, `page.tsx`) so `/account/login` and `/account/unauthorized` are **not** wrapped by `requireAccountMemberPage` (Next merges route groups under the same `account/` URL segment). Public auth surfaces: `src/app/(public-account)/account/login` and `.../unauthorized`.
- **Login:** `/account/login?next=` — `next` restricted to paths under `/account` (excludes `/account/login` and `/account/unauthorized`). Unauthenticated portal access redirects there with encoded `next`.
- **Unauthorized:** `/account/unauthorized` for authenticated users with no eligible memberships.
- **Cookie:** `vestroo_active_account_id` — httpOnly, `sameSite: lax`, `path: /account`, `secure` in production; set via server action `switchActiveAccountAction` after server-side membership check. Single-membership: no `cookies().set` in RSC (Next.js allows cookie writes only in Server Actions / Route Handlers); `resolveActiveAccount` ignores the cookie when `memberships.length === 1`. Default active account when cookie missing/invalid (multi): **sort by `customer_accounts.name` asc, then `id` asc** (see `account-portal-auth.ts`).
- **`accepted_at`:** Portal membership query requires **`accepted_at IS NOT NULL`** (migration `20260419120000_*` — null = invite pending). Note: **`account_ids_for_current_user()`** in `20260420120000_*` does **not** filter on `accepted_at`; the app gate is **stricter** so pending invites do not see `/account` until accepted.
- **Account switcher:** `AccountSwitcher` only when `memberships.length > 1`; single membership → no switcher (label only in body via “Active organisation” on home).
- **RLS intent:** All membership reads use **`createUserServerClient()`** (member JWT). RLS on `customer_accounts` / `customer_account_members` uses **`account_ids_for_current_user()`** (`profile_id = auth.uid()`, SECURITY DEFINER helper — `20260420120000_vst14_customer_account_members_rls_recursion_fix.sql`). Future portal data loads must filter by **`activeAccountId`** and must not trust client-supplied account ids without verifying membership (same helper + action pattern as the switcher). **Full** multi-account RLS regression / smoke is **15A.9** in [`docs/epic-15.md`](../epic-15.md); see epic **§6** “Portal RLS gap”.
- **Verification:** `npm run lint` (warnings only, pre-existing in other files). `npx tsc --noEmit` reports existing repo issues (Playwright/tests, etc.); **no errors** in new account portal files (filtered).
