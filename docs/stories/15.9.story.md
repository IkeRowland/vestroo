## Story

- As **ops / engineering**, we need **automated, repeatable proof** that an **account member** session for **Account A** **cannot** **SELECT** rows belonging to **Account B** on **portal-scoped** tables (**`bookings`** linked via **`customer_account_id`**, **`booking_quotes`** via the booking join, **`customer_account_members`** for the wrong **`account_id`**, **`customer_accounts`** the user does not belong to), so that **US-A1** cross-org guarantees stay **green in CI** and regressions are caught before ship (**epic §6 / §7**).

## Acceptance Criteria (ACs)

1. **Survey current smoke (gap):** **[`supabase/smoke_rls.sql`](../../supabase/smoke_rls.sql)** today performs **structural** RLS checks, policy inventory, and **behavioural** JWT matrices (**12.8 Q3** `bookings` **INSERT**, **12.9** `booking_quotes`, **13.12** finance statuses with a **single** `customer_accounts` fixture, **14.1**, etc.). **AC:** Document in **Progress Notes** that **no** section currently asserts **portal cross-account negative `SELECT`** (member of **one** account cannot read **another** account’s rows). This story **closes that gap**.

2. **Execution pattern:** New assertions use **`SET LOCAL ROLE authenticated`**, **`perform set_config('request.jwt.claim.sub', …, true)`**, and **`request.jwt.claim.role` = `authenticated`** — **consistent** with existing blocks (e.g. **`$bookings_insert_q3$`** in the same file). Prefer **`SET LOCAL`** / **`set_config(..., true)`** for transaction-scoped JWT simulation as already used. **Rollback:** remain inside the script-wide **`BEGIN` … `ROLLBACK`** so fixtures are **not** persisted (same as current file footer).

3. **Fixture model (document one chosen approach in Progress Notes):** Either **(A)** one **`auth.users` / `profiles`** identity **member of Account A only**, with **Account B** owning “foreign” rows; **or** **(B)** one identity **member of both** accounts **plus** a **second** identity **member of Account B only** — use **(A)** for **cross-tenant denial** tests (user **not** in B’s `account_ids_for_current_user()` set). If **(B)** is introduced for a future “dual membership” positive check, **document** that **RLS intentionally** exposes **all** memberships (see AC6); **15A.9** minimum is **(A)** for **negative** paths.

4. **`bookings` — cross-account `SELECT`:** With JWT **`sub`** = user who is **only** a member of **Account A**, **`SET LOCAL ROLE authenticated`**, assert **`SELECT` … `WHERE id = :booking_b_id`** (a **`client_type = 'account_client'`** booking with **`customer_account_id` = Account B**) returns **zero rows** (RLS filter), **not** an error — align with Postgres RLS semantics used elsewhere in the file. Optionally assert a **positive** control: same user can **`SELECT`** a booking for **Account A** when a row exists.

5. **`booking_quotes` — cross-account via booking:** Create (as superuser) a **`booking_quotes`** row attached to the **Account B** booking. As the **Account-A-only** member JWT, assert **`SELECT` … `WHERE id = :quote_id`** returns **zero rows**. Positive control: quote on **Account A** booking visible.

6. **`customer_account_members` / `customer_accounts` — wrong tenant:** As **Account-A-only** member JWT, assert **`SELECT` from `customer_account_members` where `account_id` = Account B** (and/or **`(account_id, email)`** key for a B-only member row) returns **zero rows**. Assert **`SELECT` from `customer_accounts` where `id` = Account B** returns **zero rows**. **Positive:** rows for **Account A** visible.

7. **RLS vs “active account” (precision):** Policies **`bookings_select_account_member`** and **`booking_quotes_select_account_member`** scope by **`customer_account_id in (select account_ids_for_current_user())`** — i.e. **all** accounts the user is a **member** of, **not** the portal **httpOnly** active-account cookie. **AC:** In **Dev guidance** / **Progress Notes**, state explicitly that **this smoke does not** simulate **`vestroo_active_account_id`**; it proves **no cross-org read** for a user **not** in the target account. **App-layer** “wrong active id” / URL tampering is primarily **15.1 / 15.4 / 15.7** server checks and **15A.10** E2E — cite; **optional** follow-up: a **separate** test or doc note if product requires **stricter** DB behaviour than “all memberships visible under RLS.”

8. **Deliverable location:** Implement the new section in **[`supabase/smoke_rls.sql`](../../supabase/smoke_rls.sql)** unless a **strong** justification exists (e.g. file size / CI time / shared DB without `auth` schema) for a sibling **`smoke_rls_portal.sql`**; a sibling **must** include updating **[`scripts/run-smoke-rls.mjs`](../../scripts/run-smoke-rls.mjs)** (today it reads **only** `supabase/smoke_rls.sql` — see **line ~131**) and **`npm run smoke:rls`** contract — default **extend the single file**.

9. **Failure ergonomics:** On assertion failure, use **`RAISE EXCEPTION`** with prefix **`[smoke_rls]`** and fields **`table=`**, **`policy=`** (or `detail=portal_isolation`), **`role=authenticated`** — consistent with existing **`[smoke_rls] FAIL …`** style in the file header (**lines ~38–39**).

10. **Traceability:** Maps to **[`docs/epic-15.md`](../epic-15.md)** **US-A1** (RLS + two-account verification), catalogue **15A.9**, **§6** mitigation, **§7** smoke DoD.
