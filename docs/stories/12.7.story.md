- **Q4 — Two-layer enforcement:** **Client** validation blocks submit when the **resolved** account booking requires a PO; **server** rejects or normalises invalid payloads on **`createBooking`** (and any other **server entrypoint** that can set **`client_type='account_client'`** with **`customer_account_id`** without a PO); **`can_dispatch_account_booking()`** remains the **authoritative** guardrail for **dispatch** — **no** reliance on UI-only checks for security or finance closure.
- **Walk-in:** **`client_type='walk_in'`** (no **`customer_account_id`**) — **`purchase_order_ref`** stays **optional**; PO requirement applies **only** when an account is linked (**US-E1** line **160**).
- **Copy:** Parameterise **`{Account}`** with the **display name** from the same source the user sees for the account (e.g. **`customer_accounts.name`** or snapshot **`name`** — align with **12.5** / **12.6** conventions): *"{Account} requires a purchase order reference for every booking."*
- **E2:** Ops dispatch block for **`po_required_and_missing`** must be **visible**, **actionable** (staff understands missing PO / wrong account config), and consistent with existing **`buildOpsActionFailure`** / toast patterns — not a silent **`NOT_DISPATCHABLE`** generically.

## Story

- As **finance**, I need **PO capture** when the **corporate account** requires it, so that **dispatch cannot proceed** while **`can_dispatch_account_booking`** would return **`po_required_and_missing`** — closing the gap between **booker intent** and **guardrail** (**Q4**).
- As a **booker** on an account that requires POs, I need the **booking form** to **require** the PO field **before submit** with **clear copy** so I know **why** the field matters.
- As **ops staff**, when I attempt **dispatch / assign-to-run** on an account booking that is missing a PO, I need a **clear UI block** tied to the **`po_required_and_missing`** reason (not a vague “not dispatchable” message) so I can **fix data** or **request PO** before retrying (**E2**).

## Acceptance Criteria (ACs)

### US-E1 — PO validation & dispatch guardrail (Theme E, **Q4**)

1. **Client-side required PO:** When the booking’s **resolved** linkage is **`client_type='account_client'`** with **`customer_account_id`** set **and** the resolved account has **`default_po_required=true`**, the booking form’s **purchase order** field is **required** — client-side validation **blocks submit** until non-blank (trim) value.

2. **Form error copy:** Validation messaging explains **why**, using (or equivalent intent to): *"{Account} requires a purchase order reference for every booking."* — **`{Account}`** substituted with the **account display name** visible in context.

3. **Server + dispatch path:** If the form is **bypassed** (API / tampered request / alternate action), **`createBooking`** (and any other relevant **server actions** that accept **`purchaseOrderRef`** / write **`purchase_order_ref`** for **account** bookings — discover call sites) **reject** or coerce to error when PO is required and missing; on **ops dispatch** (`**assignBookingToRun**` and related paths in **`src/actions/opsDispatch.ts`**), when the booking is an **account** booking, evaluate **`public.can_dispatch_account_booking(booking_id)`** (or equivalent RPC wrapper) **before** treating the row as dispatchable, and when the second column is **`po_required_and_missing`**, return **E2**-quality failure with **explicit** user-facing copy mapping that reason (distinct from “must be paid” / generic **`NOT_DISPATCHABLE`**).

4. **Walk-in optional:** For **`client_type='walk_in'`** (no **`customer_account_id`**), **`purchase_order_ref`** / form PO field remains **optional** — no **Q4** requirement.
