# Story 2.1: Route Management

## Status: Done

## Story

- As an **administrator**
- I want to **create, edit, activate, and deactivate predefined shuttle routes (origin/destination pairs) via PayloadCMS**
- so that **I can manage the available routes that travelers can book without requiring technical knowledge or code changes**

## Acceptance Criteria (ACs)

1. **AC1:** The system MUST provide a PayloadCMS collection for Routes that allows administrators to:
   - Create new routes with origin and destination names
   - Edit existing route details
   - Activate routes (make them available for booking)
   - Deactivate routes (hide them from booking without deletion)

2. **AC2:** Each Route MUST have the following required fields:
   - `origin_name` (string): Display name for the pickup location (e.g., "OR Tambo Airport")
   - `destination_name` (string): Display name for the drop-off location (e.g., "Sandton City")
   - `base_price` (number): Base price for the route
   - `is_active` (boolean): Flag to activate/deactivate the route
   - `slug` (string): Auto-generated SEO-friendly URL slug (e.g., "or-tambo-to-sandton")

3. **AC3:** The Route collection MUST include an optional `seo_content` field (RichText) for custom landing page content.

4. **AC4:** The Route collection MUST be restricted to Admin-only access using PayloadCMS Access Control functions.

5. **AC5:** The PayloadCMS admin interface MUST provide a stable, low-latency editing experience (NFR.2.1).

6. **AC6:** All Route data MUST be persisted in Supabase (PostgreSQL) database via PayloadCMS.

7. **AC7:** The Route collection MUST validate that:
   - Origin and destination names are unique per route (no duplicate routes)
   - Base price is a positive number
   - Slug is auto-generated and URL-safe

8. **AC8:** The admin interface MUST display active routes separately from inactive routes for easy management.

## Dev Technical Guidance

### PayloadCMS Collection Structure

This story requires creating a PayloadCMS collection for Routes. Reference the PayloadCMS documentation for Next.js Native integration. The collection should be defined in `src/collections/Routes.ts` following PayloadCMS 3.0 patterns.

**Key Technical Details:**

1. **Collection Location:** `src/collections/Routes.ts` (see `docs/project-structure.md` for directory structure)

2. **Data Model Reference:** See `docs/data-models.md#Route` for the Route interface structure:
   ```typescript
   export interface Route {
     id: string;
     origin_name: string;      // e.g., "OR Tambo Airport"
     destination_name: string; // e.g., "Sandton City"
     base_price: number;
     is_active: boolean;
     slug: string;             // Auto-generated for SEO: "or-tambo-to-sandton"
     seo_content: RichText;    // Custom content for the landing page
   }
   ```

3. **Access Control:** All admin routes are protected via **Supabase Auth** middleware (see `docs/operational-guidelines.md#Security-Best-Practices`). The PayloadCMS Access Control functions must restrict Routes collection to Admin-only users. Reference PayloadCMS Access Control documentation for implementation patterns.

4. **Database:** Routes will be stored in Supabase PostgreSQL via PayloadCMS. The Supabase adapter should be configured in `payload.config.ts`. Ensure `SUPABASE_SERVICE_ROLE_KEY` is set in environment variables (see `docs/environment-vars.md`).

5. **Slug Generation:** The slug field should be auto-generated from `origin_name` and `destination_name` using a beforeValidate hook. Format: lowercase, replace spaces with hyphens, remove special characters. Example: "OR Tambo Airport" + "Sandton City" → "or-tambo-airport-to-sandton-city".

6. **Validation:** Use PayloadCMS field validation and custom hooks to:
   - Ensure origin/destination pair uniqueness
   - Validate base_price is positive
   - Generate and validate slug format

7. **Admin UI Configuration:** Configure field labels, descriptions, and grouping in the collection definition. Use PayloadCMS admin UI customization options to improve UX (see `docs/architecture.md#Component-View` for admin panel context).

8. **Testing:** Manual QA is acceptable for admin panel functionality per `docs/operational-guidelines.md#Testing-Requirements`. However, consider adding basic validation tests for slug generation and duplicate prevention logic.

See `docs/environment-vars.md` for complete environment variable documentation.

### Security Considerations

- All Route operations MUST be restricted to Admin users via PayloadCMS Access Control
- Admin authentication is handled by Supabase Auth middleware (see `docs/operational-guidelines.md#Security-Best-Practices`)
- Input validation MUST be performed using PayloadCMS built-in validation and custom hooks
- Never expose admin credentials or service role keys to client-side code

### Performance Considerations

- PayloadCMS admin interface should provide low-latency editing experience (NFR.2.1)
- Consider indexing `slug` and `is_active` fields in Supabase for faster queries
- Use PayloadCMS Local API for efficient data access (no HTTP overhead)
