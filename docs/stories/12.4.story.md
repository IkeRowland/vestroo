## Story

- As **ops staff**, I need **fresh booking rows** on the unified **`/ops/bookings`** list, so that **I trust what I see** without guessing whether a new booking landed (**US-C1**).

## Acceptance Criteria (ACs)

### US-C1 — Realtime & E2 alignment (Theme C)

1. **Realtime subscription (`public.bookings`):** On **`/ops/bookings`**, subscribe to **`postgres_changes`** on **`public.bookings`** for **`INSERT`** and **`UPDATE`** (event filter or equivalent so deletes are out of scope unless already required elsewhere). Subscription is active only for the **ops staff session** on that route (client mounted for the bookings surface). **New** and **updated** rows that RLS allows the session to read are reflected in the UI **within ~3 seconds** of the DB commit **without** a manual full-page refresh by the user. Implementation: **either** debounced **`router.refresh()`** (coalesce bursts; document debounce ms in PR) **or** a **merge-into-list** client pattern that preserves **12.3** URL chip state — **document the chosen approach and rationale in the PR** (include comparison to board debounce note in **`docs/realtime-and-notifications.md`** if using refresh).

2. **Fallback when realtime unavailable / disabled:** If realtime cannot be established, enters a faulted state, or is **not used** (see **Feature flag**), the page still meets **E2** trust: **explicit refresh** control (consistent with other ops list surfaces) plus **visible data-freshness** indicator aligned with **`OpsDataFreshnessBar`** / **`docs/ops-data-freshness.md`** — **no silent staleness** (staff must never be left believing the list is live when it is not).

3. **Teardown & memory:** On **route change** and **unmount**, remove channels / clear timers / cancel debounces so **subscriptions do not leak**. Document verification steps: **manual** navigation away from **`/ops/bookings`** and back; optional **Playwright** assertion that channel teardown runs (or network/subscription count heuristic — document what was run).

4. **Authenticated realtime & RLS:** Use the project’s established **browser** Supabase client for ops (same pattern as **`OpsBoardRealtimeBridge`** — e.g. **`createClientClient`** from **`src/lib/supabase/client.ts`**), not anon keys embedded ad hoc. **RLS** must filter realtime payloads: **non-staff** sessions must **not** receive staff booking rows; reference **Epic 11 E1** policy propagation and existing **`smoke_rls`** mindset in PR / story notes (no bypass).

### Cross-cutting — Documentation (**normative**)

5. **`docs/ops-data-freshness.md`:** Add the **`/ops/bookings`** row to the index table: **Realtime + RSC** (or **RSC + explicit refresh** when bridge inactive), channels/triggers column describing **`public.bookings` INSERT/UPDATE** and debounced refresh or merge pattern, **Stale UX & recovery** column matching **AC2** and **parity intent** with **`/ops/board`** row (**E2**).

### Cross-cutting — Feature flag (**conditional**)

6. If the team uses an **environment variable or feature flag** to **disable Supabase Realtime globally** for ops (or for this route), the implementation **must** take the **non-subscription** path while still satisfying **AC2** (explicit refresh + freshness bar — **no silent staleness**). **Do not invent** new env names in this story: **discover** any existing flag in-repo during dev; if none exists, document in PR that behaviour is gated only by subscription success/failure unless a flag is introduced in the same change.
