# Story 1.1: Booking Search & Quote Interface

## Status: Done

## Story

- As a **traveler**
- I want to **select my pickup and drop-off locations, passenger count, date, and time through an intuitive booking widget**
- so that **I can receive an instant, accurate, non-negotiable quote for my shuttle service**

## Acceptance Criteria (ACs)

1. **AC1:** The system MUST provide a booking widget interface that allows users to:
   - Select Pick up location (with Google Maps autocomplete)
   - Select Drop off location (with Google Maps autocomplete)
   - Optionally enter Flight Number if the origin is an airport
   - Select Passenger Count (number of passengers)
   - Select Date (pickup date)
   - Select Time (pickup time)

2. **AC2:** The booking widget MUST integrate with Google Maps Places Autocomplete API to provide location suggestions as the user types.

3. **AC3:** When the user submits the search form with all required fields, the system MUST:
   - Validate all inputs (client-side and server-side)
   - Calculate route distance/time using Google Maps Distance Matrix API
   - Query PayloadCMS for base pricing based on route
   - Return an instant, accurate, non-negotiable quote

4. **AC4:** The quote calculation MUST be performed server-side via a Next.js Server Action (`calculateQuote`) to ensure accuracy and security.

5. **AC5:** The booking widget MUST be mobile-first responsive and follow the design goals: modern, friendly, corporate, professional, trustworthy, and efficient.

6. **AC6:** All user inputs MUST be persisted in Zustand store (`useBookingStore`) to maintain state across the booking flow.

7. **AC7:** The interface MUST provide clear visual feedback during quote calculation (loading state).

8. **AC8:** Error handling MUST be implemented for:
   - Invalid location selections
   - API failures (Google Maps, PayloadCMS)
   - Network errors
   - Validation errors

### Technical Context

**State Management:**
- Use Zustand for booking state persistence. See `docs/front-end-state-management.md` for the BookingState interface structure.
- The store should persist: origin, destination, date, passengers, flightNumber (optional).
- Store will be extended in future stories for quote and booking details.

**Google Maps Integration:**
- **Places Autocomplete:** Client-side, requires `NEXT_PUBLIC_GOOGLE_MAPS_KEY`. Use `use-places-autocomplete` library or native Google Maps Script Loader. See `docs/api-reference.md#google-maps-platform`.
- **Distance Matrix API:** Server-side only, uses the same API key but should be restricted server-side. Returns distance and duration for route calculation.
- Reference: `docs/api-reference.md` for API details.

**Server Actions Pattern:**
- Use Next.js Server Actions (not API routes) for quote calculation. See `docs/front-end-api-interaction.md#server-actions`.
- Server Action should be in `src/actions/calculateQuote.ts`.
- Input validation using Zod schemas (both client and server). See `docs/operational-guidelines.md#security-best-practices`.

**Component Architecture:**
- Follow Atomic Design: Primitives in `src/components/ui/`, feature components in `src/features/booking/components/`. See `docs/front-end-component-guide.md`.
- Use Shadcn/UI components as base (Button, Input, Calendar, etc.). Style with Tailwind CSS.
- All booking-related components should be Client Components ("use client").

**Routing:**
- Booking search page: `/book/search` in `(app)` route group. See `docs/front-end-routing-strategy.md`.
- After successful quote, navigate to `/book/quote` (to be implemented in next story).

**Data Models:**
- Route data structure: See `docs/data-models.md#route-point-to-point`.
- Quote result should include: price, vehicle options, estimated duration, route details.

**Pricing Calculation Logic:**
- Query PayloadCMS for route base_price (if route exists in CMS).
- Use Google Distance Matrix to get actual distance/duration.
- Calculate final price: base_price + (distance-based multiplier if applicable).
- This logic must be 100% unit tested. See `docs/operational-guidelines.md#testing-requirements`.

**Error Handling:**
- Client-side: Display validation errors inline with form fields.
- Server-side: Return structured error responses from Server Action.
- Handle API failures gracefully with user-friendly messages.

**Performance Considerations:**
- Lazy load Google Maps scripts (only when AddressAutocomplete is mounted).
- Optimize quote calculation to minimize latency (cache route data if possible).
- Follow mobile-first design for Core Web Vitals (LCP < 2.5s). See `docs/epic-1.md#related-non-functional-requirements`.

**Accessibility:**
- All form inputs must have associated labels (Shadcn FormItem handles this).
- Keyboard navigation must work throughout the form.
- Screen reader support for autocomplete suggestions.
- See `docs/front-end-coding-standards.md#accessibility-ax-implementation`.
