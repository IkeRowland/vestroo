# Story 2.2: Pricing Management

## Status: Done

## Story

- As an **administrator**
- I want to **set and adjust pricing dynamically based on route, vehicle type, and potential date/time factors via PayloadCMS**
- so that **I can manage pricing strategies and respond to market conditions without requiring technical knowledge or code changes**

## Acceptance Criteria (ACs)

1. **AC1:** The system MUST provide a PayloadCMS collection for Vehicle Types that allows administrators to:
   - Create vehicle types (e.g., Sedan, Van, SUV) with display names
   - Set base price multipliers for each vehicle type (relative to route base_price)
   - Activate/deactivate vehicle types
   - Define passenger and luggage capacity for each vehicle type

2. **AC2:** The system MUST provide a PayloadCMS collection for Pricing Rules that allows administrators to:
   - Create pricing rules that apply to specific routes or all routes
   - Define date/time-based pricing adjustments (e.g., peak hours, weekends, holidays)
   - Set percentage-based price modifiers (e.g., +20% for peak hours, -10% for off-peak)
   - Activate/deactivate pricing rules
   - Set priority/order for rule application when multiple rules apply

3. **AC3:** Each Vehicle Type MUST have the following required fields:
   - `name` (string): Display name (e.g., "Premium Sedan", "8-Seater Van")
   - `slug` (string): Auto-generated URL-safe identifier
   - `price_multiplier` (number): Multiplier applied to route base_price (e.g., 1.0 for base, 1.5 for premium)
   - `passenger_capacity` (number): Maximum number of passengers
   - `luggage_capacity` (number): Maximum number of luggage pieces
   - `is_active` (boolean): Flag to activate/deactivate the vehicle type
   - `image_url` (text, optional): URL to vehicle image for display in booking flow

4. **AC4:** Each Pricing Rule MUST have the following required fields:
   - `name` (string): Descriptive name for the rule (e.g., "Peak Hours", "Weekend Surcharge")
   - `route_id` (relationship, optional): Specific route this rule applies to (null = applies to all routes)
   - `vehicle_type_id` (relationship, optional): Specific vehicle type this rule applies to (null = applies to all vehicle types)
   - `price_modifier_percent` (number): Percentage adjustment (e.g., 20 for +20%, -10 for -10%)
   - `day_of_week` (select, optional): Specific day(s) of week (Monday-Sunday, or "All")
   - `start_time` (text, optional): Start time in HH:mm format (e.g., "08:00" for 8 AM)
   - `end_time` (text, optional): End time in HH:mm format (e.g., "18:00" for 6 PM)
   - `start_date` (date, optional): Rule start date (for seasonal/holiday pricing)
   - `end_date` (date, optional): Rule end date (for seasonal/holiday pricing)
   - `priority` (number): Rule priority/order (lower number = higher priority, applied first)
   - `is_active` (boolean): Flag to activate/deactivate the rule

5. **AC5:** The Vehicle Types and Pricing Rules collections MUST be restricted to Admin-only access using PayloadCMS Access Control functions.

6. **AC6:** The pricing calculation logic MUST:
   - Start with the route's `base_price`
   - Apply vehicle type `price_multiplier` to get vehicle-specific base price
   - Apply all matching active pricing rules in priority order (cumulative)
   - Return the final calculated price

7. **AC7:** The pricing calculation MUST be accessible via:
   - A reusable function in `src/lib/calculations.ts` for server-side calculations
   - Integration with the booking flow (Story 1.1/1.2) to display accurate quotes
   - PayloadCMS hooks or server actions for admin preview/testing

8. **AC8:** All Vehicle Types and Pricing Rules data MUST be persisted in Supabase (PostgreSQL) database via PayloadCMS.

9. **AC9:** The PayloadCMS admin interface MUST provide a stable, low-latency editing experience (NFR.2.1).

10. **AC10:** The system MUST validate that:
    - Vehicle type price multipliers are positive numbers (minimum 0.1)
    - Pricing rule modifiers are reasonable (suggested range: -50% to +200%)
    - Time ranges are valid (start_time < end_time)
    - Date ranges are valid (start_date <= end_date)
    - Priority values are positive integers

### Pricing Calculation Algorithm

The pricing calculation follows this sequence:

1. **Base Price:** Fetch route `base_price` from Routes collection
2. **Vehicle Multiplier:** Apply vehicle type `price_multiplier`:
   ```
   vehicle_base_price = route.base_price * vehicle_type.price_multiplier
   ```
3. **Rule Matching:** Find all active PricingRules where:
   - `route_id` matches OR is null (applies to all routes)
   - `vehicle_type_id` matches OR is null (applies to all vehicles)
   - `day_of_week` matches pickup date OR is "All"
   - `start_time` and `end_time` (if provided) contain pickup time
   - `start_date` and `end_date` (if provided) contain pickup date
4. **Rule Application:** Sort matching rules by `priority` (ascending, lower = higher priority)
5. **Cumulative Modifiers:** Apply each rule's `price_modifier_percent` cumulatively:
   ```
   final_price = vehicle_base_price
   for each rule in sorted_rules:
     final_price = final_price * (1 + rule.price_modifier_percent / 100)
   ```

### PayloadCMS Local API Usage

For server-side pricing calculations, use PayloadCMS Local API:

```typescript
import { getPayload } from 'payload'
import config from '@payload-config'

const payload = await getPayload({ config })

// Fetch route
const route = await payload.findByID({
  collection: 'routes',
  id: routeId,
})

// Fetch vehicle type
const vehicleType = await payload.findByID({
  collection: 'vehicle-types',
  id: vehicleTypeId,
})

// Fetch matching pricing rules
const rules = await payload.find({
  collection: 'pricing-rules',
  where: {
    and: [
      { is_active: { equals: true } },
      // ... additional filters for route, vehicle, date/time
    ],
  },
  sort: 'priority',
})
```

### Validation Examples

**Vehicle Type Validation:**
- `price_multiplier`: Must be >= 0.1 (prevents zero or negative multipliers)
- `passenger_capacity`: Must be >= 1 (integer)
- `luggage_capacity`: Must be >= 0 (integer, allows 0 for passenger-only vehicles)

**Pricing Rule Validation:**
- `price_modifier_percent`: Suggested range -50 to 200 (allows -50% discount to +200% surcharge)
- Time range: If both `start_time` and `end_time` provided, `start_time` must be < `end_time`
- Date range: If both `start_date` and `end_date` provided, `start_date` must be <= `end_date`
- Priority: Must be >= 1 (integer, lower numbers = higher priority)

### Deviation Analysis

**From Epic 2.2 Requirements:**
- Epic states: "set and adjust pricing dynamically based on route, vehicle type, and potential date/time factors"
- Story expands this into two collections (VehicleTypes and PricingRules) for better separation of concerns
- This allows more flexible pricing management than a single pricing table
- Vehicle types are separated to allow reuse across multiple routes
- Pricing rules use a flexible rule-based system rather than fixed pricing tables

**Rationale:**
- Separation of vehicle types from pricing allows vehicle management independent of pricing
- Rule-based pricing system provides maximum flexibility for future pricing strategies
- Priority-based rule application allows complex pricing scenarios (e.g., peak hours + holiday surcharge)
- Optional route/vehicle specificity allows both global and route-specific pricing rules
