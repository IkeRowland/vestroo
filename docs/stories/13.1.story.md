## Story

- As **fulfilment staff**, I need **dispatch** for **account** bookings when the **SQL guardrail** says the account is healthy, so that **I am not blocked by walk-in prepayment rules** when terms are invoice-based (**US-A1**, **[`docs/epic-13.md`](../epic-13.md)** **§1**).
- As a **maintainer**, I need **`isBookingDispatchable`** to **branch on `client_type`** and **`assignBookingToRun`** to **surface reason codes** consistently, so that **13.2+** can build UI and overrides on a **stable contract** (**§3 Phase 1**, **Theme F 13.1**).

## Acceptance Criteria (ACs)

### US-A1 — Dispatch branching & SQL authority (Theme A)

1. **`isBookingDispatchable(booking)` branches on `booking.client_type`:** For **`walk_in`**, behaviour matches the **current** paid gate (**`status='paid' AND payment_status='paid'`**) with **no** regression — **[`docs/epic-13.md`](../epic-13.md)** **§4 Theme A — US-A1** (first **AC**).

2. **Account path uses SQL:** For **`account_client`**, the function calls **`can_dispatch_account_booking(booking.id)`** (or project-equivalent RPC wrapping the SQL function) and returns **`{ ok: true }`** when the SQL layer indicates success **`(true, 'ok')`**; otherwise returns **`{ ok: false, reason: <reason_code> }`** matching the SQL contract — **US-A1** (second **AC**).

3. **`assignBookingToRun` error surface:** The existing **`assignBookingToRun`** server action surfaces account guardrail failure via a new **`OpsActionError`** variant — e.g. **`NOT_DISPATCHABLE_ACCOUNT`** — carrying a structured **`reasonCode`** (and **not** only a generic “not dispatchable” message) — **US-A1** (third **AC**). Align naming with **`src/features/ops/ops-action-errors.ts`** conventions.

4. **No duplicate TS guardrails:** **No** second implementation of the reason-code matrix in TypeScript; TypeScript **delegates** to **`can_dispatch_account_booking()`** for the account path — **US-A1** (fourth **AC**).

5. **Unit tests per reason-code path:** Automated tests cover **each** reason-code branch returned from the **TypeScript** integration (mapping/RPC outcomes), including **`ok`** and representative failure codes emitted by **`can_dispatch_account_booking()`** — **US-A1** (fifth **AC**). (Exact code list follows SQL from **[`docs/epic-12.md`](../epic-12.md)** / migration — e.g. `account_on_hold`, `account_suspended`, `contract_expired`, `contract_not_yet_active`, `po_required_and_missing`, `credit_limit_exceeded`, `overdue_invoices`, etc.)

### Cross-cutting

6. **Traceability to Phase 1 / Theme F:** Implementation is traceable to **[`docs/epic-13.md`](../epic-13.md)** **§3** Phase **1** (**Guardrail integration**) and **§4 Theme F** row **13.1** (**3 pts**, Theme **A**, depends on Epic **12** complete).

7. **Primary code touchpoints:** Changes land in (or adjacent to) **`src/actions/opsDispatch.ts`**, **`src/lib/ops-booking.ts`** (**`isBookingDispatchable`**), and **`src/features/ops/ops-action-errors.ts`** — **[`docs/epic-13.md`](../epic-13.md)** **§8 References**.
