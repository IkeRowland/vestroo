# Story 2.3: Booking Review

## Status: Done

## Story

- As an **administrator**
- I want to **view, search, filter, and manage all incoming bookings via PayloadCMS**
- so that **I can monitor booking activity, respond to customer inquiries, and manage booking statuses without requiring technical knowledge or database access**

## Acceptance Criteria (ACs)

1. **AC1:** The system MUST provide a PayloadCMS collection for Bookings that allows administrators to:
   - View all bookings in a list/grid view with key information (booking ID, customer, route, date/time, status, amount)
   - Access detailed booking information via detail view
   - See related data (route name, vehicle type, customer details) through relationships

2. **AC2:** The system MUST provide search functionality that allows administrators to:
   - Search bookings by booking ID/reference
   - Search bookings by customer name or email
   - Search bookings by payment reference
   - Search bookings by flight number (if provided)

3. **AC3:** The system MUST provide filtering capabilities that allow administrators to:
   - Filter bookings by status ('pending' | 'paid' | 'confirmed' | 'completed' | 'cancelled')
   - Filter bookings by date range (pickup date)
   - Filter bookings by route
   - Filter bookings by vehicle type
   - Combine multiple filters simultaneously

4. **AC4:** The system MUST allow administrators to manage booking statuses by:
   - Updating booking status (e.g., from 'paid' to 'confirmed', or to 'cancelled')
   - Viewing status change history (if implemented via PayloadCMS versioning)
   - Preventing invalid status transitions (e.g., cannot go from 'cancelled' to 'paid')

5. **AC5:** The Booking collection MUST display related information clearly:
   - Route origin and destination names (via route_id relationship)
   - Vehicle type name (via vehicle_type_id relationship)
   - Customer information (via user_id relationship or embedded fields)
   - Formatted pickup date/time
   - Formatted total amount (currency)

6. **AC6:** The Booking collection MUST enforce access control:
   - Only administrators can view, search, filter, and manage bookings
   - Access control implemented via PayloadCMS Access Control functions
   - Admin authentication handled by Supabase Auth middleware

7. **AC7:** The Booking collection MUST provide adequate performance for admin operations:
   - List view should load efficiently with pagination
   - Search and filter operations should complete within reasonable time (< 2 seconds)
   - Detail view should load booking information quickly

## Dev Technical Guidance

### PayloadCMS Collection Structure

This story requires creating a PayloadCMS collection for Bookings. Reference the PayloadCMS documentation for Next.js Native integration. The collection should be defined in `src/collections/Bookings.ts` following PayloadCMS 3.0 patterns.

**Key Technical Details:**

1. **Collection Location:** `src/collections/Bookings.ts` (see `docs/project-structure.md` for directory structure)

2. **Data Model Reference:** See `docs/data-models.md#Booking` for the Booking interface structure:
   ```typescript
   export interface Booking {
     id: string;
     user_id: string (Relation to Users);
     route_id: string (Relation to Routes);
     vehicle_type_id: string (Relation to VehicleTypes);
     status: 'pending' | 'paid' | 'confirmed' | 'completed' | 'cancelled';
     passenger_count: number;
     pickup_datetime: Date;
     flight_number?: string;
     total_amount: number;
     payment_reference: string;
   }
   ```

3. **Access Control:** All admin routes are protected via **Supabase Auth** middleware (see `docs/operational-guidelines.md#Security-Best-Practices`). The PayloadCMS Access Control functions must restrict Bookings collection to Admin-only users. Reference PayloadCMS Access Control documentation and follow the same pattern used in Routes collection (Story 2.1) and VehicleTypes/PricingRules collections (Story 2.2).

4. **Database:** Bookings will be stored in Supabase PostgreSQL via PayloadCMS. The Supabase adapter should already be configured in `payload.config.ts`. Ensure `SUPABASE_SERVICE_ROLE_KEY` is set in environment variables (see `docs/environment-vars.md`).

5. **Relationship Fields:**
   - `route_id`: Relationship to Routes collection (created in Story 2.1)
   - `vehicle_type_id`: Relationship to VehicleTypes collection (created in Story 2.2)
   - `user_id`: Relationship to Users collection (PayloadCMS default or Supabase Auth users)

6. **Field Configuration:**
   - `status`: Use PayloadCMS `select` field type with enum values: 'pending', 'paid', 'confirmed', 'completed', 'cancelled'
   - `pickup_datetime`: Use PayloadCMS `date` field type with time enabled
   - `passenger_count`: Use PayloadCMS `number` field type (integer, minimum 1)
   - `total_amount`: Use PayloadCMS `number` field type (decimal, minimum 0)
   - `flight_number`: Use PayloadCMS `text` field type (optional)
   - `payment_reference`: Use PayloadCMS `text` field type

7. **Admin UI Configuration:**
   - Configure default list view columns to show most important information
   - Use PayloadCMS field customization to format dates, currency, and relationship displays
   - Configure field labels, descriptions, and grouping for improved UX
   - Enable search on relevant fields (ID, payment_reference, flight_number, customer info)
   - Configure filters for status, date range, route, vehicle type

8. **Search Configuration:**
   - PayloadCMS provides built-in search functionality
   - Configure `searchableFields` in collection config to include: `id`, `payment_reference`, `flight_number`
   - For customer search, may need to configure search on relationship fields or use custom search logic
   - Reference PayloadCMS search documentation for relationship field searching

9. **Filtering Configuration:**
   - PayloadCMS provides built-in filtering via `where` queries
   - Configure filter UI in admin panel for: status (select), pickup_datetime (date range), route_id (relationship), vehicle_type_id (relationship)
   - Multiple filters can be combined automatically by PayloadCMS
   - Reference PayloadCMS filtering documentation

10. **Status Management:**
    - Status field should be editable in admin UI
    - Consider adding validation hooks to enforce business rules (e.g., cannot cancel already completed bookings)
    - PayloadCMS versioning can track status change history (optional but recommended)
    - Reference PayloadCMS hooks documentation for `beforeChange` validation

11. **Performance Optimization:**
    - Configure pagination (default: 10-20 items per page, configurable)
    - Ensure Supabase database indexes exist on frequently queried fields:
      - `status` (for status filtering)
      - `pickup_datetime` (for date range filtering and sorting)
      - `route_id` (for route filtering)
      - `vehicle_type_id` (for vehicle type filtering)
    - Use PayloadCMS Local API for efficient queries (no HTTP overhead)
    - Consider using `depth` parameter wisely when fetching relationships to avoid over-fetching

### Deviation Analysis

**From Epic 2.3 Requirements:**
- Epic states: "view, search, filter, and manage all incoming bookings"
- Story expands "manage" to specifically mean status management, as full booking editing (changing route, vehicle, dates) may not be appropriate business logic
- Story focuses on admin interface via PayloadCMS, which provides built-in search, filter, and list/detail views
- Status management is the primary "management" action, as other booking fields should generally be immutable after creation

**Rationale:**
- PayloadCMS provides robust admin UI out of the box for viewing, searching, and filtering
- Status management is the most common admin action needed for bookings
- Immutability of core booking fields (route, vehicle, date, amount) maintains data integrity and audit trail
- Future stories can add more advanced management features if needed (e.g., cancellation workflows, refund processing)
