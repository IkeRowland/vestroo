# Story 5.5: Capstone manager feature mapping onto Vestroo ops backlog

## Status: Done

**Dependencies:** **[Story 5.4](5.4.story.md)** — **Done**; living artifact **[`docs/capstone-admin-to-ops-mapping.md`](../capstone-admin-to-ops-mapping.md)** covers **capstone admin → `/ops/*` only** — **do not** duplicate admin-only rows here; **cross-link** that doc from the manager mapping intro. **[Stories 5.1–5.3](5.1.story.md)** — **Done** (ops shell, design system ADR/parity, CRUD primitives) — context for **`ops-nav-config.ts`**, **`requireOpsStaffPage`**, and Tailwind ops patterns.

## Story

- As a **product or engineering lead**
- I want a **dedicated mapping artifact** from capstone **`frontend-manager`** routes and integrations (**`docs/capstone-reference/frontend-manager`**) to Vestroo **`/ops/*`** and **`/field/*`** behaviour, data, and backlog
- so that **manager-style** reference IA (dashboard, drivers, customers, schedules, ratings, rich `/admin`) is **traceable** without conflating **dispatcher vs admin** concerns, **corporate shuttle / Epic 9** vocabulary stays enforced (**NFR.5.4**), and engineers **do not** treat reference **JWT-in-`localStorage`**, **axios-to-Nest**, or **Firebase** as Vestroo defaults (**NFR.5.3**)

## Epic traceability (source)

**From `docs/epic-5.md` — FE.5.5:** The product MUST map **manager** capabilities to **`/ops/*` and `/field/*`** behaviour and data. The mapping MUST explicitly cover **reference routes** under `frontend-manager/src/app/(dashboard)/`: **drivers** (`/drivers`, `[id]`); **customers** (`/customers`); **vehicles** (`/vehicles`); **road routes** (`/routes`); **driver/shift schedule** (`/schedule`); **recurring timetable / line schedules** (`/schedules` — separate from chauffeur shift **`/schedule`**; map only where Vestroo offers equivalent **structured timetable** services, else mark **not applicable**); **ratings / feedback** (`/rating` — filters include **service type**: hourly, scenic route, share, destination); **profile** (`/profile`); **rich admin dashboard** (`/admin` — **UserCard**, **CountChart**, **AttendanceChart**, **FinanceChart**, **EventCalendar**, **Announcements**). The reference **manager home** (`src/app/page.tsx`) repeats sidebar + **UserCard** + **AttendanceChart**; treat **dashboard / analytics home** as a first-class mapping target (e.g. **`/ops`** or **`/ops/board`**) even if Vestroo defers charts. **REST constants** in reference still expose **bookings** paths (`constants/api.ts`, `routers.ts`); map **booking visibility** to Vestroo **search, fulfil, trips, or reporting** even when no single `/bookings` page exists. Gaps MUST list **proposed** Vestroo routes or widgets. **Dispatcher vs manager** role boundaries and **menu visibility by role** MUST be noted where the single app merges both. **Internationalization**: reference manager uses **i18next**; state whether Vestroo internal tools require locale switching or **English-only MVP**.

**Constraining NFRs:**

- **NFR.5.3:** The artifact MUST **not** present **client-stored JWTs**, **Nest REST + axios** as the default first-party ops pattern, or **Firebase** as Vestroo’s default for staff tools; it MUST align with **`requireOpsStaffPage`**, **`requireChauffeurPage`**, Supabase session clients, and **Server Actions** (see **`docs/ops-console.md`**, **`docs/field-tools.md`**, **FE.5.9**).
- **NFR.5.4:** Use **Epic 4 / VST** vocabulary (corporate shuttle, service routes, trips, bookings, chauffeurs, fleet) — not legacy **public-transit** or capstone **demo** naming when describing Vestroo targets.
- **Corporate shuttle / Epic 9:** Rows tied to reference **transit-demo** or **Bus\***-shaped modules (e.g. recurring **line** timetables) MUST use **deferred / N/A / Epic 9 optional patterned-shuttle gate** language where Vestroo has no equivalent structured timetable product — consistent with **[Epic 9](epic-9.md)** and the admin mapping’s **Epic 9** discipline.

## Acceptance Criteria (ACs)

1. **Artifact location and filename:** Add a **new** primary document **`docs/capstone-manager-to-vestroo-mapping.md`**. The doc MUST be **self-contained for manager reference scope**; it MUST **cross-link** **[`docs/capstone-admin-to-ops-mapping.md`](../capstone-admin-to-ops-mapping.md)** in the intro and MUST **not** re-list **admin-only** FE.5.4 rows (e.g. admin **`/router`**, **`/money`**, **`/cal`**, category CRUD) except where **one line** is needed to say “see admin mapping.” The doc MUST start with **purpose**, **scope** (manager + bookings constants + dashboard home), **sources** (paths under **`docs/capstone-reference/frontend-manager`**), and **last updated** date.

2. **Master mapping table — required columns:** Include a **single primary table** (appendix tables allowed only if they avoid duplicating the main row set). Every **data row** MUST include at minimum:
   - **Reference screen / capstone route** (e.g. `/drivers`, `/schedule`, …).
   - **Capstone implementation pointer** (e.g. **`src/app/(dashboard)/drivers/page.tsx`**).
   - **Vestroo target** — primary **`/ops/*`** and/or **`/field/*`** route(s), or explicit **no dedicated route** / **server-only** / **deferred** / **Epic 9** wording.
   - **Status** — exactly one of **`implemented`**, **`partial`**, **`not started`**, **`not applicable`** (footnoted definitions; **not applicable** = no planned equivalent in shuttle MVP / gated to Epic 9).
   - **Vestroo-preferred term / naming** (**NFR.5.4**) where reference labels differ.
   - **Supabase / platform** — tables or views **by name**, Storage if relevant, **RLS** note at **high level** — no policy SQL dumps.
   - **Story / epic traceability** — **VST-***, **5.x**, **Epic 6–9** where backend or realtime ownership matters.

3. **Mandatory route rows (one table row each at minimum):** The primary table MUST include at least one row for each reference **`(dashboard)`** route:
   - **`/drivers`** and **`/drivers/[id]`** (chauffeur / driver roster vs field execution).
   - **`/customers`** (B2B or traveller lists — map to Vestroo data surfaces honestly).
   - **`/vehicles`** (manager fleet view — **cross-reference** admin mapping for deep parity; avoid duplicating admin row prose).
   - **`/routes`** (road / service routes — **corporate shuttle** geometry vocabulary; **Epic 9** for fixed-line/bus demo concepts).
   - **`/schedule`** (driver/shift schedule in reference — map to **`/ops/roster`**, **`/ops/calendar`**, **`/field`**, or gaps).
   - **`/schedules`** (recurring **bus**-style schedules in reference — **N/A** or **deferred** with **one-line rationale** if Vestroo has **no structured timetable** product).
   - **`/rating`** (service-type filters: hourly, scenic route, share, destination).
   - **`/profile`** (manager profile — align with shell chrome vs standalone page).
   - **`/admin`** (UserCard, CountChart, AttendanceChart, FinanceChart, EventCalendar, Announcements).

4. **Manager home / dashboard row (mandatory):** At least **one** row MUST map **`docs/capstone-reference/frontend-manager/src/app/page.tsx`** (sidebar + **UserCard** + **AttendanceChart**) to Vestroo **dashboard / analytics home** targets (e.g. **`/ops` → `/ops/board`**, **`/ops/calendar`**) and MUST note **widget / chart deferral** explicitly if no charts exist yet.

5. **Bookings — API constants row (mandatory):** At least **one** row MUST cite **`docs/capstone-reference/frontend-manager/src/constants/api.ts`** (**`BASE_PATHS.BOOKINGS`**, **`API_ENDPOINT.BOOKINGS`**) and **`docs/capstone-reference/frontend-manager/src/constants/routers.ts`** (**`ROUTERS.MANAGE.BOOKINGS.BASE`** → **`/manage/bookings`**) and MUST map **booking visibility** to Vestroo **`/ops/search`**, **`/ops/fulfil`**, **`/ops/trips`**, and **reporting / audit** concepts — stating clearly that there may be **no** single **`/ops/bookings`** list route.

6. **Dispatcher vs admin + menu visibility:** Include a **subsection** (not only table footnotes) explaining **Vestroo `dispatcher` vs `admin`** vs capstone **`admin` / `manager`** merge: reference **`Menu.tsx`** `visible: ["admin" | "manager"]` vs Vestroo **`ops-nav-config.ts`** `visibleRoles`, **`requireOpsStaffPage`**, and **`getOpsAdminForAction`** for **admin-only** Server Actions (e.g. compliance DSR). MUST satisfy **NFR.5.5** intent: **nav hints must not imply access** to **server-forbidden** actions.

7. **Internationalization:** Include a short **subsection** on reference **i18next** vs Vestroo internal tools: state product stance (**locale switching** vs **English-only MVP** for **`/ops`** and **`/field`**) and any **future** i18n guardrails — without implementing UI.

8. **Prioritisation / gaps:** Close with a **“Backlog / prioritisation / proposed routes or widgets”** subsection listing **highest-signal gaps** (e.g. dedicated **customers** list, **ratings** dashboard, **manager analytics** widgets, **recurring timetable** if ever product-approved under Epic 9).

9. **Documentation index:** Add a bullet under **`docs/index.md`** (e.g. next to the existing admin mapping bullet) linking **`docs/capstone-manager-to-vestroo-mapping.md`** with one-line description (**FE.5.5** manager mapping).

10. **Epic cross-link:** In **`docs/epic-5.md`**, under **FE.5.5**, add a **single** sentence or bullet pointing to **`docs/capstone-manager-to-vestroo-mapping.md`** as the **living artifact** (do not duplicate the full matrix in the epic body).

11. **Integration posture (concise):** Include a brief **reference vs Vestroo** integration note (manager **AuthContext** / axios / JWT patterns vs **Supabase + server gates**) — **aligned with FE.5.9**; **does not** replace **Epic 6** BE.6.1 module matrix.

12. **Verification method:** Author MUST **cross-check** Vestroo route claims against **`src/app/(ops)/ops/**`** and **`src/app/(field)/`** App Router trees and **`src/features/ops/ops-nav-config.ts`**; align **Status** cells with repo reality and note **intentional gaps**.
