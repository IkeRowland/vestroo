# Epic 5: Align Ops Console & Field Experience with Capstone Reference UX, IA, and Feature Expectations

## Description

**Product framing (locked):** Vestroo is a **corporate shuttle** company—**B2B / contracted** transport, chauffeured and shuttle-style services—not a **fixed-route public mass-transit** or **public line-network** operator. Epic 5 planning, **`/ops/*` IA**, and **user-facing** copy MUST **not** frame Vestroo as **public line service**, **scheduled mass transit**, or a **public boarding-point network** product. Use **corporate shuttle** language (**approved pickup/drop-off**, **service corridors**, **zones**, **waypoints**, **client runs**, **bookings**, **trips**, **fleet**). Vendored **capstone reference** code may retain legacy **Nest** module names or **`cline_docs/`** filenames for traceability only; those identifiers **do not** describe Vestroo’s product.

This epic closes the gap between the **unified Vestroo Next.js application** (`src/app` route groups: `(marketing)`, `(app)` booking, `(ops)` staff console at `/ops/*`, `(field)` chauffeur web at `/field/*`) and the **reference capstone frontends** vendored under `docs/capstone-reference/` (**frontend-admin**, **frontend-manager**, **frontend-driver**). The reference README describes three separate web apps (admin, manager, customer) plus a **React Native (Expo)** driver app; the current product intentionally converges roles into one deployable but **does not yet match** the reference **information architecture**, **dashboard shell patterns**, **manager-style light workspace layout**, or **native driver modality**. The capstone admin/manager UIs use **Ant Design** for density and components; **Vestroo does not adopt Ant** for `/ops`—implementation uses **Tailwind CSS** with **Radix primitives** and, where useful, **shadcn-style** patterns so ops stays aligned with the rest of the app and Vestroo branding. The reference apps integrate with a **NestJS REST API**, **JWT in `localStorage`**, **axios**, **Firebase Storage** (e.g. vehicle images in admin), and **socket.io** on the driver app; Vestroo uses **Supabase**, **server-first staff auth**, and **Server Actions**—those differences MUST be documented in the mapping work so engineers do not copy reference **auth or transport** blindly. **`docs/capstone-reference/frontend-customer`** traveller-facing parity stays under **Epic 1** and related VST stories. **`cline_docs/`**, the reference **`backend/`**, and **`document/`** diagrams are **in scope for traceability** via **FE.5.10** (matrix index—not implementation of every reference domain); backend implementation parity is **Epic 6–9**. Work here is **outcome-focused**: a credible internal console shell (sidebar, top bar, wayfinding), a documented **Tailwind-based ops design system** (tokens + parity spec vs reference *interactions*), a **feature backlog map** from capstone admin/manager/driver **screens and integrations** onto Vestroo ops and field capabilities, and **responsive, accessible** polish—without blindly copying **legacy capstone demo naming** where Epic 4 / VST domain vocabulary already supersedes it.

## Goals

* Establish an **operations console shell** consistent with professional dashboard expectations (persistent **sidebar**, **top bar**, **breadcrumbs** or equivalent hierarchy cues), reducing reliance on a single horizontal wrap-nav header.
* **Implement and document** a **`/ops/*` design system on Tailwind** (utility tokens + shared components): short **ADR** (decision: no Ant Design in ops), **parity spec** vs capstone admin/manager *behaviour* (tables, forms, modals, notifications, density), and **token-level** guidance so new ops pages stay visually consistent with Epic 4 / VST.
* Produce a **traceability matrix** from capstone README feature lists **plus concrete reference routes and modules** (see FE.5.4–FE.5.6, FE.5.9) to **current and planned** Vestroo routes and epics, so gaps are visible and prioritised—including **manager dashboard / analytics** (KPI cards, charts, optional finance and calendar widgets on reference `/` and `/admin`) and **stack/integration** differences (REST/JWT/Firebase/socket vs Supabase/Realtime).
* Deliver **FE.5.11** staff ops capabilities (users/roles, clients, fleet, routes/service areas, bookings) in **`/ops/*`**, backed by **Epic 6** data and server patterns.
* Improve **field (`/field/*`)** ergonomics on the web (responsive layout, touch targets, offline-tolerant patterns where feasible) while **recording** the strategic choice vs **React Native** driver app for production chauffeurs.
* Raise **accessibility** and **responsive** quality for internal tools to a defined baseline (keyboard, focus, contrast, landmark regions).
* **Coordinate** with **Epic 6–9**: front-end IA and mapping (this epic) plus **backend**, **real-time**, **integrations**, and **Epic 9** (deferred capstone modules / optional patterned shuttle) together cover **full reference-project traceability** where product approves implementation.

## User Stories / Requirements

### FE.5.1: Ops console information architecture & navigation shell

The system MUST replace the **primary** ops navigation model from a **single header row of equal-weight links** with a **dashboard shell**: collapsible **sidebar** (or equivalent persistent nav) grouping areas by domain (e.g. fulfilment, fleet, people, finance/compliance, configuration), plus a **top bar** for global actions (search, notifications placeholder, profile/sign-out). The shell MUST expose **current location** via **breadcrumbs** or a clearly labeled page title hierarchy. **Deep links** and **browser back/forward** MUST remain valid. The implementation MUST be scoped to **`(ops)`** so marketing and public booking layouts are unchanged.

Where Vestroo distinguishes **multiple staff roles** with different capabilities, navigation MUST support **role-aware visibility** of items (reference pattern: `frontend-manager` `Menu.tsx` `visible: ["admin" | "manager"]`) while **server-side authorization** remains authoritative—see NFR.5.5.

### FE.5.2: Ops design system — Tailwind + Radix (+ shadcn-style parity)

**Decision (locked):** **`/ops/*` MUST use Tailwind CSS** as the styling foundation, with **Radix UI** primitives (existing `@radix-ui/*` usage extended as needed) and **optional shadcn/ui**-style components copied into `src/features/ops` or shared UI per [Repository conventions](repo-conventions.md)—**Ant Design MUST NOT** be introduced for **`/ops/*`** or **authenticated `/field/*`** (Epic 5 internal consoles) unless a future ADR explicitly revises this epic.

The team MUST **document** (short **ADR** in `docs/` + link from [Documentation Index](index.md)): rationale (single stack with marketing/booking, brand fit, bundle size), scope (ops + field internal shells), and **non-goals** (pixel-match to capstone Ant theme).

The team MUST publish a **parity spec** (same `docs/` note or companion doc) aligned to reference **interaction** patterns from **frontend-admin** and **frontend-manager**, not their visual theme: **data tables** (sort, filter, pagination, loading/empty/error); **forms** (labels, validation, async submit, disabled states); **feedback** (modal, drawer/sheet, toast or inline alert pattern—reference manager uses **Sonner**); **density and spacing tokens** for list-heavy screens; **dashboard widgets** (stat/KPI cards, chart containers with consistent height/legend/empty states—reference uses **Recharts** and **DevExtreme**); **scheduling/calendar surfaces** (reference: **react-big-calendar**, **react-calendar**, **EventCalendar** on manager `/admin`). Optional: **global route loading** affordance (reference: **nextjs-toploader**) if product wants parity with perceived navigation speed. The spec MUST define **CSS variables or Tailwind theme extensions** (colours, radii, typography, sidebar width) for ops so implementations do not drift.

Implementation MUST favour **shared ops primitives** (e.g. page header, filter row, table wrapper, primary/secondary actions) built with Tailwind classes and composition—new ops pages MUST reuse them.

### FE.5.3: Component patterns for CRUD and data-heavy ops views

Ops screens that present **lists, filters, and edit flows** MUST converge on **consistent Tailwind-based patterns** per FE.5.2: loading and empty states, error surfaces, confirm destructive actions, and **accessible** table/list semantics. New or refactored ops features MUST reuse **shared ops primitives** (not one-off styled blocks). **Reference implementations** in `docs/capstone-reference/frontend-admin` and `frontend-manager` MAY be cited as **interaction references**, not as sources of copy or domain naming that conflict with Vestroo Epic 4 vocabulary.

### FE.5.4: Capstone admin feature mapping onto Vestroo ops backlog

The product MUST maintain a **mapping artifact** (table or section in an existing planning doc) from capstone **admin** capabilities to **`/ops/*` routes**, **Supabase capabilities**, and **story IDs** (e.g. VST-*). The artifact MUST include at least these **reference screens** from `frontend-admin` (see `Sidebar.tsx` and `src/app/(page)/`): **user management** (home `/`); **vehicle categories** (`/category`); **vehicles** (`/vehicles`, detail `[id]`); **staff profile** (`/profile`); **road and service-area authoring** (`/router`, including **Leaflet** map + routing/editing patterns—express in **corporate shuttle** terms such as corridors, zones, and approved pickup/drop-off points; **do not** carry over reference labels or IA tied to fixed public-transit networks); **cash flow / pricing** (`/money`—config and price rows); **price calculator** (`/cal`); **trip management** (`/trip`). It MUST also map **media uploads**: reference uses **Firebase Storage** for vehicle images (`utils/firebase`)—document the **Vestroo equivalent** (e.g. Supabase Storage) and any UX gap. **Forgot-password** and **login** flows exist in the reference admin; map to **`/ops/login`** (and equivalents) for parity of **recovery and session** expectations, without adopting JWT-in-localStorage as the security model. Each row MUST state **implemented**, **partial**, or **not started** and the **Vestroo-preferred term** where it differs from the reference. Outcomes: no silent feature drift; clear prioritisation for pricing, categories, **map/geo authoring**, and **calculator** tools if absent.

* **Living artifact:** [Capstone admin → ops mapping](capstone-admin-to-ops-mapping.md) — maintained as the master table; the epic body does not duplicate the full matrix here.

### FE.5.5: Capstone manager feature mapping onto Vestroo ops backlog

The product MUST map **manager** capabilities to **`/ops/*` and `/field/*`** behaviour and data. The mapping MUST explicitly cover **reference routes** under `frontend-manager/src/app/(dashboard)/`: **drivers** (`/drivers`, `[id]`); **customers** (`/customers`); **vehicles** (`/vehicles`); **road routes** (`/routes`); **driver/shift schedule** (`/schedule`); **recurring timetable / line schedules** (`/schedules` in reference—separate from chauffeur shift **`/schedule`**; map only where Vestroo offers equivalent **structured timetable** services, else mark **not applicable**); **ratings / feedback** (`/rating`—filters include **service type**: hourly, scenic route, share, destination); **profile** (`/profile`); **rich admin dashboard** (`/admin`—**UserCard**, **CountChart**, **AttendanceChart**, **FinanceChart**, **EventCalendar**, **Announcements**). The reference **manager home** (`src/app/page.tsx`) repeats sidebar + **UserCard** + **AttendanceChart**; treat **dashboard / analytics home** as a first-class mapping target (e.g. `/ops` or `/ops/board`) even if Vestroo defers charts. **REST constants** in reference still expose **bookings** paths (`constants/api.ts`, `routers.ts`); map **booking visibility** to Vestroo **search, fulfil, trips, or reporting** even when no single `/bookings` page exists. Gaps MUST list **proposed** Vestroo routes or widgets. **Dispatcher vs manager** role boundaries and **menu visibility by role** MUST be noted where the single app merges both. **Internationalization**: reference manager uses **i18next**; state whether Vestroo internal tools require locale switching or English-only MVP.

* **Living artifact:** [Capstone manager → Vestroo mapping](capstone-manager-to-vestroo-mapping.md) — maintained as the master table for **FE.5.5**; the epic body does not duplicate the full matrix here.

### FE.5.6: Field (chauffeur) web experience vs reference driver app modality

The system MUST document **modality strategy**: reference **frontend-driver** is **Expo / React Native** (**NativeWind**), with **expo-location**, **expo-notifications**, **react-native-maps** + directions, and **socket.io-client** across multiple concerns; current **field** is **mobile-web**. The mapping MUST enumerate reference **screens and real-time domains**: **Home**; **Schedule** (with **ScheduleContext** / pause-confirm patterns); **Notifications** tab (**badge** unread count, **NotificationContext**); **Conversations** list + **ConversationDetail** (**useConversationSocket** and related hooks); **Trip tracking** (**TripTrackingScreen**, **useTripSocket**, **useTrackingSocket**); **Trip history** (implemented in codebase though one tab is commented in `AppNavigator`); **Profile**; **shared itinerary** (**useSharedItinerarySocket**). Cross-link **Vestroo** [Realtime and notifications](realtime-and-notifications.md) (VST-9) when mapping sockets to **Supabase Realtime** or recording gaps. The team MUST deliver a **short assessment** (pros/cons, MVP vs phase 2 native) and, for the **web MVP**, MUST improve **responsive** layout (breakpoints, sticky actions, safe-area awareness where applicable), **large touch targets**, and **obvious task flows** (today’s trips, accept/decline if applicable, check-in/out). If **in-app chat** or **push notifications** are out of scope for web, that MUST be explicit in the mapping doc and replaced with an **interim** pattern (e.g. deep link to approved channel, SMS policy per field tools doc) where product requires it.

* **Living artifact:** [Capstone driver → field mapping](capstone-driver-to-field-mapping.md) — modality strategy, screen/socket matrix, interim comms, and verification notes for **FE.5.6**; the epic body does not duplicate the full table here.

### FE.5.7: Responsive polish for internal routes

**`/ops/*` and authenticated `/field/*`** MUST be usable on **tablet widths** without horizontal clipping of primary actions: sidebar collapse behaviour, scroll regions, and modals/drawers MUST be verified at agreed breakpoints. **Marketing and booking** flows remain governed by existing epics; this story targets **internal** consoles.

### FE.5.8: Accessibility baseline for ops and field shells

The ops and field layouts MUST meet an agreed **WCAG-oriented baseline**: **landmarks** (`header`, `nav`, `main`), **skip link** where practical, **visible focus**, **aria-label** on icon-only controls, **color contrast** for dark ops chrome (or light theme variant if adopted), and **keyboard** access to sidebar collapse and primary nav. Automated checks (e.g. axe in CI or manual test script) SHOULD be referenced in project docs.

### FE.5.9: Reference stack & integration mapping (no blind porting)

The traceability work MUST include a **short integration appendix** (same mapping artifact or linked doc) covering: **NestJS REST + axios + JWT in `localStorage`** (admin `ClientLayout` / manager `AuthContext`) vs Vestroo **Supabase + `requireOpsStaffPage` / server sessions**; **Firebase Storage** (admin vehicle images) vs **Supabase Storage** (or other); **socket.io** driver namespaces/events vs **Supabase Realtime** channels and policies. Purpose: teams may reuse **UI/IA ideas** from `docs/capstone-reference` but MUST **not** copy **auth tokens, API clients, or socket URLs** without a designed Vestroo equivalent. Reference **dependencies** worth awareness for parity discussions: admin **Leaflet / leaflet-routing-machine / leaflet-editable**; manager **TanStack Query**, **Redux**, **Zustand**, **MUI** date pickers, **Leaflet** on some flows—Vestroo chooses **Tailwind-era** equivalents per FE.5.2 rather than importing this stack wholesale.

* **Living artifact:** [Capstone reference — stack & integration](capstone-reference-stack-integration.md) — canonical **FE.5.9** appendix (comparison tables, anti-patterns, UI dependency inventory); **Nest module matrix:** [Capstone backend module matrix](capstone-backend-module-matrix.md) (**BE.6.1** / **FE.5.10**, also linked from [Epic 6](epic-6.md)).

### FE.5.11: Core staff operations capabilities (`/ops`)

This story is the **canonical checklist** for what **authorised staff** (roles as product defines: e.g. dispatcher, ops admin) MUST be able to do in the **`/ops/*` console**, using patterns from **FE.5.2–FE.5.3**. It **supplements** FE.5.4–FE.5.5 (capstone mapping) by stating **Vestroo outcomes** regardless of reference gaps.

The system MUST support, at minimum as **implemented or explicitly backlog-scoped** with status in the traceability matrix:

1. **Staff users and roles** — Create and maintain **internal** staff identities, **assign roles** or permissions, deactivate access; align with **Supabase Auth** / custom claims and **`requireOpsStaffPage`** (see [Epic 6](epic-6.md) **BE.6.5**, **BE.6.7**). **Chauffeur / field** accounts remain distinct from generic “users” where VST separates them.
2. **Corporate clients** — Create and manage **client / account** records (companies, contract metadata as product requires) for **B2B** shuttle context; link to bookings where applicable.
3. **Vehicles and categories** — Create, **categorise** (classes/types), update, and retire **fleet** records; optional **media** per **FE.5.4** (Supabase Storage).
4. **Service routes and service areas** — Create and manage **corporate shuttle** routing concepts: corridors, zones, approved pickup/drop-off, **pricing-relevant** path data—**not** public-transit **fixed-line** or **mass-transit network** IA (see **Epic 9** for deferred capstone-only modules).
5. **Bookings** — Create (where staff-assisted booking is required), search, filter, view detail, and perform **lifecycle** actions (assign, modify, cancel, fulfil) consistent with **Epic 1** / **VST-6** and existing **`/ops/search`**, **`/ops/fulfil`**, **`/ops/trips`** behaviour; gaps MUST be listed in the matrix.
6. **Related staff workflows** — As product requires: **roster / calendar**, **drivers or chauffeurs**, **invoicing hooks**, **compliance**, **experiences**, **vehicles**, **board**—already partially present under **`/ops/*`**; FE.5.11 MUST **not** duplicate every VST story but MUST ensure the **Epic 5 sidebar IA** (FE.5.1) **groups** these domains and **no critical** admin activity is **orphaned** without a mapped route or **explicit deferral**.

* **[Epic 6](epic-6.md) [BE.6.7](epic-6.md#be67-data-and-server-actions-for-staff-ops-fe511)** / **[Story 6.7](stories/6.7.story.md)** maintains the same matrix’s **data-owner** depth (**Supabase tables**, **RLS**, **Server Actions / Route Handlers**) **alongside** **[Story 5.11](stories/5.11.story.md)** **UI** checklist work — **separate** from the **FE.5.10** **24-module** matrix pointer in **[Capstone backend module matrix](capstone-backend-module-matrix.md)**.

## Related Non-Functional Requirements

* **NFR.5.1:** Maintainability — FE.5.2 MUST minimise **duplicate** table/form implementations across ops pages; shared Tailwind-based wrappers or tokens MUST be defined and used.
* **NFR.5.2:** Performance — Ops UI MUST keep **client JS lean**: prefer Server Components where possible, lazy-load heavy client-only widgets (maps, large tables), and avoid pulling duplicate component libraries; Tailwind MUST remain **purged** to used classes in production builds.
* **NFR.5.3:** Security — Navigation and shell changes MUST **not** weaken **`requireOpsStaffPage`** / **`requireChauffeurPage`** gates; role checks remain server-first.
* **NFR.5.4:** Consistency — Epic 4 / VST **domain language** takes precedence over capstone **demo naming** in user-visible strings and new routes.
* **NFR.5.5:** Authorization alignment — Any **role-based nav** (FE.5.1) MUST match **server-enforced** permissions: users MUST NOT see links to actions they cannot perform; hidden routes MUST still **403/redirect** if hit directly.

## Design Goals

* **Overall vision:** Internal tools should feel like a **coherent operations product**—predictable chrome, scannable lists, and clear hierarchy—not a collection of standalone pages linked from a dense header.
* **Reference posture:** **frontend-admin** informs **dark sidebar + data-dense** layouts and **map-first route and service-area authoring** for **corporate shuttle** (implemented with **Tailwind tokens**, not Ant); **frontend-manager** informs **light content workspace + sidebar + top bar** rhythm and **dashboard analytics density** (cards + charts + calendar strip) on home/`/admin`; **frontend-driver** informs **tab-based task flow**, **notification + messaging** affordances, and **live trip / map** patterns adapted to web where native is deferred.
* **Critical views:** Ops shell (all `/ops/*` children), field shell (`/field/*` after login), and the **mapping documents** tying capstone features to Vestroo backlog.
* **Responsiveness:** Tablet-first for ops dispatch use; field flows **mobile-first** within the web constraint.
